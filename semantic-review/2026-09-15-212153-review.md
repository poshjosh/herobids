# Legal-isolation migration c4.9c→c4.9g — holistic cross-slice review

The c4.9c→c4.9g arc completes the extraction of the last trading reads and the last trading write out of herobids and behind the Traderton REST boundary: per-agent outcomes/decisions/decision-failures now read boundary tools, the blueprint→bot instantiate WRITE moved over an authored `instantiate_bot` tool with a deterministic idempotent actorId, the last local `venue_accounts` binding read was removed in favour of the boundary's owner-guard, and the worker's remaining indirect trading-repo access (find_instrument, decision-failure/llm-artifact persistence, instrument-population, orphan-cleanup) was re-pointed or dropped. The individual slices are internally sound: the idempotency derivation is a correct RFC-4122 v5, the g1 removal preserves both the rejection-return and the in-memory breaker, the find_instrument re-point rides an already-wired boundary seam, and the connectionId→creatorId attribution rescope is applied consistently and honestly recorded. The problem is at the aggregate level, which is exactly where per-slice review is blind.

Watch for:
- **CRITICAL (confirmed):** the "ZERO trading-table runtime access" precondition is FALSE. The herobids worker still has 20 live runtime read/write sites against `market_assessment_*` tables across 6 files — a table family the migration's own re-scope note (011) lists in the FULL drop set. The final audit enumeration silently dropped `market_assessment_*`, so the precondition was declared met against a narrower set than the one it re-scoped to.
- **HIGH (confirmed):** docs/003's atomicity-split entry claims "concurrent duplicates collapse" as exact parity, but the post-boundary second local tx re-acquires no advisory lock and re-runs no replay check; a genuinely concurrent same-key pair races the `uq_bpir_user_key` unique index and the loser gets an uncaught 23505 → 500. The claim is stronger than the code.
- **MEDIUM (confirmed):** the g3 (instrument-population deleted, Deferred) / g4 (find_instrument re-pointed, fail-closed) pairing creates an ordering hazard: if Traderton has not wired `populateInstrumentsFromVenues` at startup before cutover, every re-pointed find_instrument reads an empty `instruments` table and fails closed.

**Verdict**: NEEDS_CHANGES

## High-level view

The isolation invariant does not hold in aggregate. The 17 core trading tables (bots/fills/positions/venue_accounts/user_credentials/journal_events/decisions/orders/execution_plans/decision_failures/llm_decision_artifacts/balance_snapshots/decision_contexts/instruments/token_safety_overrides/reconciliation_events) are genuinely clean in herobids `apps/**/src` — I independently re-grepped both direct Drizzle access and the named repository classes and found only comments, `Buffer.from`, and type-only `$inferSelect` imports. But `market_assessment_*` — which the coordinator's own table list and docs/011's re-scope note both place in the drop set — has extensive live worker access that no slice in this arc touched. The precondition-met claim in docs/011 enumerates the audited set and stops at `reconciliation_events`, silently omitting the market-assessment family. This is the single fact that gates the whole table-drop, and it is wrong as stated.

The slices themselves compose correctly where they interact. c4.9d-FG's `instantiate_bot` owner-guard genuinely subsumes c4.9f-ready's removed local `venue_accounts` check — both reach the same 404 rejection, and the boundary tool resolves ownership server-side. c4.9g's find_instrument re-point targets a boundary tool that genuinely exists on the Traderton side and rides the same `ctx.tradertonBoundary.invoke` seam that account/price/risk-limits/market-data already use.

The divergence ledger is mostly consistent with the code. The connectionId→creatorId attribution rescope is applied uniformly on the Traderton side (every agent-bot scope resolves `creatorType='agent' AND creatorId=agentId`), and its behavioural narrowing (dropping cross-attribution of other actors' bots via shared connections) is recorded, verified against the pre-migration commit, and ruled ledger-only. The one place the ledger overstates the code is the instantiate atomicity-split's concurrency claim.

The idempotency design is sound on the happy and crash-retry paths: the deterministic UUIDv5 actorId makes the boundary fingerprint stable so a retry replays the stored botId and a different body still 409s locally before the boundary. The gap is only the true-concurrent window, which the tests do not exercise (the "concurrent" test is serialized by the lock and hits the local replay path).

The g1 removal is clean: every deleted `recordFailure` call sat beside a preserved rejection-return, and the in-memory `failureCounters` breaker was never coupled to the DB write, so both survive.

### instantiate_bot owner-guard subsumes the removed local venue_accounts read — coherent

c4.9f-ready removed the local `venue_accounts` binding read (existence→400, not-owned→403) on the premise that `instantiate_bot`'s own owner-scoped guard is now the authority. Tracing both sides confirms the semantics compose: the herobids handler (`blueprints.ts` ~2139-2177) keeps only the local `connections` validation (a KEEP platform table) and maps a boundary `not_found.resource` to 404 (~2432). The Traderton `instantiate_bot` performs the owner-scoped venue-account guard server-side (docs/005 + `bots.ts` insertStoppedBot path). The old 400/403 split collapses to a single 404 that does not leak whether an unowned account exists — recorded as an Intentional-divergence in 003 and covered by the updated test ("rejects an unowned venue account via the boundary (404 not_found.resource)"). Same rejection reachable, no cross-owner existence leak. This interaction is sound.

### Idempotency: happy/crash-retry converge; true-concurrent races a 500

The actorId derivation (`blueprint-idempotency.ts`) is a correct RFC-4122 §4.3 v5 UUID over a fixed namespace, with an injective length-prefixed name encoding (`${byteLen}:${userId}:${key}`) that closes the `("a","b:c")` vs `("a:b","c")` collision. Because the boundary fingerprint hashes the full payload including actorId, a stable actorId is what makes a crash-retry (boundary succeeded, local commit lost) re-send the identical fingerprint and replay the stored botId; the request-hash comparison in the first tx still 409s a different body before the boundary is ever called. Those two paths are covered by real tests (`blueprints.integration.test.ts` C5 replay, crash-retry convergence).

The gap is the genuinely concurrent same-key pair. The first `db.transaction` takes the advisory lock, checks `blueprintInstantiationRequests` for a replay, validates, and returns `proceed_bot` — then RELEASES the lock before the boundary call (correct: you must not hold a pinned connection across the ~30s round-trip). The boundary call is idempotent so both concurrent requests collapse to one bot. But the SECOND local tx that writes the idempotency + usage rows (~2437) takes NO advisory lock and re-runs NO replay check. Two requests that both cleared the first tx's replay check (because neither had committed its row yet) will both attempt `insert(blueprintInstantiationRequests)` with the same `(userId, idempotencyKey)`; the `uq_bpir_user_key` unique index (`blueprint-instantiation-requests.ts:20`) rejects the loser with a 23505, which is uncaught by the handler and surfaces as a 500. Not a double-create and not idempotency corruption — the bot is single and inert — but docs/003 claims "concurrent duplicates collapse" as exact parity, and that is stronger than the code delivers. The fix is small: wrap the second tx in the same advisory lock and re-check for the existing row (replaying it if present), or catch the unique-violation and convert it to a 200 replay. The "concurrent-duplicate" test does not catch this because it is serialized by the lock and the second request hits the local replay path (200), never the true race.

### g1 decision-failure removal — rejection-return and breaker both preserved

The diff removes the `recordFailure` helper and every call to it from `agent-decision-handler.ts`. Each removed call sat immediately after a preserved `reject(...)`/return that carries the failure code + message back to the caller (agent_paused, stale_session, dry_run_approval_mode, precondition.not_ready, authorization.denied, etc.) — only the DB persistence side-effect went. The in-memory circuit breaker is a separate mechanism (`failureCounters` Map + `breakerThresholds`, lines 33-34, 149-150) that was never tied to the DecisionFailureRepository, so it is untouched. This matches the recorded Gap (Traderton's own M1 no-op; get_agent_decision_failures returns empty until Traderton wires the write). No behaviour beyond persistence was lost; the Gap is honestly a Gap, not a disguised escalation.

### find_instrument re-point — targets a real, wired boundary seam

g4 replaces the local `instrumentRepo.search` path with `mapReadResultToToolResult(await ctx.tradertonBoundary.invoke({ toolName: 'find_instrument', payload: { query, venue, limit } }))`, fail-closed when the boundary is absent (no local fallback). The tool exists on the Traderton side (`packages/worker/src/tools/find-instrument.ts`, name registered) and is exposed over the boundary (bin.ts references find_instrument routing). `ctx.tradertonBoundary` is the same context field that account/price/risk-limits/market-data tools already invoke, so the seam is genuinely wired, not aspirational. The one caveat is cutover ordering (see below).

### g3/g4 ordering hazard at cutover

g3 DELETED the herobids startup `populateInstrumentsFromVenues` (Deferred — Traderton must wire its own copy). g4 re-pointed find_instrument at Traderton's `instruments` table, fail-closed. These two are independently correct but coupled at cutover: if Traderton's worker startup has not wired instrument population before the herobids table drop, find_instrument reads an empty `instruments` table and fails closed on every lookup — a silent capability outage for agents resolving symbols. Recorded as Deferred-required-for-cutover in 011 line 34(a), but flagging it here because it is a cross-slice sequencing dependency, not a within-slice concern: the drop cannot proceed until the Traderton population wiring is confirmed live.

### Divergence-ledger consistency

The connectionId→creatorId rescope (654-655 in 001) is applied consistently: `loadAgentBotIds` and every agent-bot-scoped tool on the Traderton side resolve `creatorType='agent' AND creatorId=agentId` (bots.ts:182/607/661/739/1318/1629; repositories.ts:220-221; journal-pg.ts:262-263). The ledger entry honestly records the behavioural narrowing (cross-attribution of other actors' bots via shared connections is dropped), notes c4.9b flagged the old join as potentially double-counting, and verifies against pre-migration commit `5b26fc1a^`. No reader remains on the old connection-linked basis. The g1/g2 Gaps and the atomicity-split Intentional-divergence are all recorded; the only ledger-vs-code mismatch is the atomicity-split's over-strong "concurrent duplicates collapse" wording called out above.
