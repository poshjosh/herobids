## 3. Design decisions (decide-and-record; none is contested)

- **D-a Key lifecycle rule.** An `idempotencyKey` names ONE logical write. It is reused only while that write's outcome is unknown (`transport_error`, `in_progress`). A terminal outcome — success or failure, retryable or not — ends the key's life; a deliberate retry after a terminal failure is a new logical write with a new key (otherwise the stored failure is replayed forever, §2).
- **D-b `requestId` is derived, not minted.** When a caller supplies `idempotencyKey` and no `requestId`, `buildEnvelope` sets `requestId = deriveRequestId({consumerId, ownerId: subject.ownerId, toolName, idempotencyKey})` — an RFC 4122 v5 UUID over `JSON.stringify([consumerId, ownerId, toolName, idempotencyKey])` under a fixed namespace. Why: (1) every re-issue reuses the same `requestId` with zero extra state; (2) CF-2 persistence reduces to "the key's domain id is persisted before the call", which existing rows already guarantee (§4) — no new table/column/Redis key (KISS); (3) owner/tool scoping means a container-supplied key (`decisionId`, `messageId`) can never collide with another owner's `requestId` on the non-owner-scoped status lookup. An explicit caller `requestId` still wins (saga keeps `operationId`). No key supplied → all three ids stay `randomUUID()` (read path unchanged).
- **D-c Compiler enforcement on the worker write port, not the client.** `idempotencyKey: string` becomes **required** on both `TradertonSideEffectBoundary.invoke` and `.invokeAndAwait` (5 consumers; cheap). `InvokeToolInput.idempotencyKey` stays optional: `TradertonClient.invoke` serves reads AND writes, and the client cannot tell them apart without a backend-specific tool list (would break the genericity invariant ahead of T1). The api's direct-client writes are handled by disposition (§4), not types.
- **D-d `ToolContext.tradertonWriteBoundary` (domain port) is unchanged.** Agent tools stay key-less; the agent-side binding mints one key per tool write (each tool makes exactly one write call, so per-binding-call == per-tool-execution). The required worker-port key forces the binding to mint it. No churn in `risk-limits.ts`/`watch.ts` or their tests.
- **D-e In-call reconcile on unknown outcome (consumes CF-2 on the synchronous path).** In `invokeAndAwait`: if the first invoke returns `transport_error` and the shared `deadlineAt` has not passed, re-issue ONCE with the identical input (same key, derived `requestId`, payload, `deadlineAt`, one `correlationId` minted per `invokeAndAwait`). The backend makes this at-most-once: it replays a stored result, reports `in_progress` (→ existing poll by the same `requestId`), or executes once if the first never arrived. If the re-issue returns `deadline.expired`, keep the original `transport_error` (outcome still unknown — §2 deadline-before-replay). Never re-issue after a terminal result (D-a). Transport-neutral: the same step works unchanged for MCP (no status endpoint). Worst-case overrun past `deadlineAt` ≤ one `requestTimeoutMs`; documented.
- **D-f Honest unknown-outcome mapping.** `mapBoundaryResultToDecisionOutcome` `transport_error` message stops claiming "the decision was not submitted"; it says the outcome is unknown and to check positions before resubmitting. `code`/`retryable` unchanged. Unknown-outcome branches log `{ requestId, idempotencyKey }` so an operator can reconcile via the status endpoint.

Record D-a, D-b, D-e as `P3-1..P3-3` in the Phase-3 `DECISIONS.md` §3 (D-c/D-d/D-f fold into IV-1's text).

## 9. Risks, observations, open questions (none blocks T0.6)

- **R1 (forward to T2.3 / D15):** deadline pre-check precedes replay (§2). On MCP the only reconcile is a same-key re-issue; after `deadlineAt` it returns `deadline.expired`, and re-issuing with a fresh deadline could *execute* a stale write that never arrived. REST has a non-executing status endpoint; MCP has none. T2.3 must decide (e.g. a non-executing status tool/resource, or accept "unknown" past the deadline). Not a T0.6 change.

Fix per D-a (per-attempt key; a repeat deprovision returns `not_found.resource`, already treated as success per lessons §7). Verify with a backend test before changing.
