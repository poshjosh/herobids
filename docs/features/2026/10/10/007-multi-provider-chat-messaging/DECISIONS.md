| DEC-50 | Schema note section 7 requires a decision for any new column. CH2W slice 2 added `conversation_messages.queued_at` (timestamptz, not null, default `now()`, migration `0085_redundant_hammerhead`), outside the schema note approved in DEC-47. It records when a row last entered `queued`: equal to `created_at` on insert, restamped by a retry claim. Why: a `queued` row whose process died before publishing must be re-publishable after `messaging.conversations.staleQueuedAfterSeconds` (default 60). If age were measured from `created_at`, a retried old message would look stale again at once and a racing second retry would claim it too. Restamping on the claim keeps the retried message fresh, so exactly one racer wins the atomic claim. Existing rows get the migration time (`now()` at migration), which is harmless: only `queued` rows are ever aged and none is expected to be in flight at migration. Accepted risk: stale-ness is compared against the clock of the API instance that stamps and the one that reads, so skew between API instances larger than `staleQueuedAfterSeconds` could make a fresh message claimable early (a duplicate publish, which the runtime does not de-duplicate) or a stuck one late. With a 60 s default and NTP-synced hosts the risk is low. Alternative if the owner declines: drop the column, age from `created_at`, and accept that a retried old message is immediately re-claimable | CH2W (slice 2 onward) | approved (owner, 2026-10-25) |
