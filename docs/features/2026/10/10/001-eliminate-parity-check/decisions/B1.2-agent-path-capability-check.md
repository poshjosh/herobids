# Decision Brief B1.2: the agent-path capability check

- **Question:** herobids's `apps/api/src/routes/agents.ts:1276` rejects an agent
  execution-mode update when the mode is `paper` and the agent's active trading
  connection is a swap venue (`validateExecutionCapability({ actorType: 'agent', ... })`
  → `execution_capability.paper_swap_not_supported`). Traderton has **no** equivalent
  check on the agent path. Should herobids drop this check (accepting the behavior
  change), keep it as a documented exception, or add a traderton-side check first?
- **Status:** PROPOSED.

## Evidence

- **The herobids check** (`routes/agents.ts:1276`): on `PATCH /agents/:id` (execution-mode
  update), it looks up the agent's active trading connection, derives the venue type via
  `venueTypeFromProvider`, and rejects `paper` + `swap` with a 400
  `execution_capability.paper_swap_not_supported`.
- **The bot paths are covered by traderton** (verified 2026-10-10): `drive-target.ts:300`
  (create) and `tools/bots.ts:1185` (create) call `validateExecutionCapability`; the
  `adjust_bot_config` path re-validates via `BotConfigSchema`'s `.refine`
  (`config/schema.ts:776-778`, rejects `venueType === 'swap' && execution.mode === 'paper'`)
  and `checkModeEscalation` (`drive-target.ts:606`). These were the basis for B1.1.
- **The agent path has no traderton equivalent** (verified 2026-10-10): the agent-direct
  `submit_decision` intake (`decision-intake.ts`) carries `executionMode` and `venueType`
  as spec fields but performs **no** paper+swap capability check; there is no
  `validateExecutionCapability` call on any agent-direct path. `grep validateExecutionCapability`
  across traderton's `packages/worker/src` returns only the bot paths and the
  `_deferred-authoring` API-route copies.
- **What the check protects:** an agent configured with `paper` execution on a swap venue
  (Jupiter/1inch). Paper mode has no price source on swap venues, so a paper+swap agent
  cannot actually trade — the check rejects the *configuration* at write time rather than
  letting the agent fail at runtime.

## Options

1. **Drop herobids's check and accept the behavior change.** The agent can be configured
   `paper` + swap; it simply won't be able to trade (paper has no swap price source). This
   is the pure de-duplication path and lets `execution-capability.ts` be deleted in B1.3.
   - Cost: a misconfigured agent is accepted at write time and fails later (or silently
     does nothing) instead of being rejected up front.
   - Reversibility: high — re-adding a check is a small change.
2. **Add a traderton-side check for the agent path, then drop herobids's.** Traderton's
   agent-direct intake (or the `start_agent_actor` / `submit_decision` path) rejects
   paper+swap with a typed boundary error; herobids maps it to the same 400. This
   preserves the behavior and keeps the check authoritative in traderton.
   - Cost: a new traderton milestone (and a herobids tag + pin bump) before B1.3 can
     delete `execution-capability.ts`.
   - Reversibility: high.
3. **Keep herobids's check as a documented exception.** Treat the `execution-capability`
   entry as a contract-package item (C-track) instead of a dead-copy delete; herobids keeps
   its local check and the mirror stays until the package lands.
   - Cost: the `domain-trading-execution-capability` entry survives longer; B1.3 is
     deferred or re-scoped.
   - Reversibility: high.

## Recommendation

**Option 1** (drop and accept), unless the paper+swap agent configuration is a real
support/UX hazard you want rejected up front. The check is a write-time convenience, not a
safety invariant: paper mode on a swap venue cannot trade, so the worst case is a
misconfigured agent that does nothing rather than a dangerous one. Dropping it is the
simplest path and unblocks B1.3 (delete `execution-capability.ts`) immediately.

If you prefer the behavior preserved, **Option 2** is the correct one (it keeps the check
authoritative in traderton, consistent with the bot paths), at the cost of a new traderton
milestone before B1.3.

## What this blocks

- **B1.3** (delete `execution-capability.ts`; remove `domain-trading-execution-capability`).
  Option 1 unblocks it now; Option 2 adds a traderton milestone first; Option 3 defers it
  to the C-track.
