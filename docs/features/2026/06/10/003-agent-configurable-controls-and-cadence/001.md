# AGENT CONFIGURABLE CONTROLS AND CADENCE

## Scope

This plan covers adding explicit, user-configurable agent fields in the create and edit flows for:

- tick interval
- max bots
- capital
- daily loss limit
- max slippage (bps)
- daily LLM token budget

It also covers the supporting runtime contract and UI guidance needed to make those fields understandable:

- tick interval is the agent's base cadence
- runtime may still slow down when idle or after failures
- derived summaries are shown alongside the inputs, especially estimated daily spend and expected cadence
- if tick interval is not explicitly set, the UI should derive and show an expected cadence instead of pretending the value is fixed

This plan intentionally excludes runtime reconfiguration after startup. These values are editable in create/edit flows only.

## Product Stance

1. The agent creation and edit forms should own the user-facing configuration for these fields.
- No separate runtime editing surface is needed.
- Values are applied when the agent is created or updated.
- If the agent is running, configuration changes remain constrained by the existing lifecycle rules.

2. Tick interval is user-controlled, but runtime still owns safety backoff.
- The value entered by the user is the base cadence.
- The worker may widen the interval when idle or after failures.
- The UI copy should preserve the wording that the agent may still slow down when idle or after failures.

3. Cost presets and explicit tick interval are separate concepts.
- `tick interval` governs cadence.
- `costPreset` governs model choice, default thinking depth, and preset-specific runtime gates.
- `dailyBudgetUsd` remains a budget input that can influence recommendations and derived summaries.
- Explicit tick interval wins over preset-derived cadence if both are present.

4. Capital means deployable allocation, not wallet balance.
- The wallet may hold more USDC than the agent is allowed to use.
- The form should communicate that capital is the amount the agent may trade with, not the full wallet balance.

5. The form should show a derived summary beside the inputs.
- Estimated daily spend is important.
- Expected cadence is especially useful when the user did not explicitly specify tick interval.
- When tick interval is specified, the summary should switch to the caveat: "may still slow down when idle or after failures".

6. i18n is required for all new labels, helper copy, validation text, and summary text.
- Add localized strings for English and the other active locales.
- Avoid hard-coded English text in the form or summary components.

## Implementation Plan

1. Define the agent configuration contract in the API layer.
- Update the agent create/update request schemas to carry the new fields explicitly.
- Keep the semantics narrow and unambiguous:
  - `tickInterval` = base cadence
  - `maxBots` = concurrency cap
  - `capital` = deployable allocation cap
  - `dailyLossLimit` = drawdown guardrail
  - `maxSlippageBps` = execution guardrail
  - `dailyLlmTokenBudget` = reasoning cost cap
- Normalize empty values and invalid values consistently on the server.
- Dependency: this is the foundation for the UI and worker payloads.

2. Thread the new fields through the agent API response model.
- Extend the flattened agent response so the web app can render the values directly.
- Preserve backward compatibility for existing rows that do not yet have the new fields.
- Ensure create/update responses return the normalized values immediately after save.
- Dependency: step 1.

3. Decide where each field lives in the form and keep the scope narrow.
- Keep these values in the agent create and edit forms only.
- Do not add runtime-editability controls.
- Keep the form grouped into a clear configuration section rather than mixing the fields into identity or model selection.
- Dependency: none, but this decision should shape the next UI tasks.

4. Update the create flow in `apps/web/src/features/agents/AgentsPage.tsx`.
- Add inputs for the six fields to the create modal.
- Prefill sensible defaults where possible.
- Show the derived summary alongside the inputs.
- Dependency: steps 1 and 2.

5. Update the edit flow in `apps/web/src/features/agents/EditAgentModal.tsx`.
- Add the same six fields to the edit modal.
- Preserve existing values when the agent already has them.
- Let users clear or update values explicitly.
- Show the same derived summary patterns used in create.
- Dependency: steps 1 and 2.

6. Add derived summary logic for cadence and daily spend.
- Build a shared helper that derives:
  - expected cadence when tick interval is unset
  - estimated daily spend from the selected cadence and budget/cost context
  - the slowdown caveat when tick interval is explicitly set
- Keep the helper deterministic and easy to test.
- Make sure the summary degrades gracefully when budget or model data is incomplete.
- Dependency: step 1.

7. Keep `costPreset` and `dailyBudgetUsd` as related but separate inputs.
- `costPreset` should remain available as a cost-policy selector, not a replacement for explicit tick interval.
- `dailyBudgetUsd` should continue to influence cost profile recommendations and derived summaries.
- If explicit tick interval exists, it should override preset-derived cadence while leaving the rest of the preset behavior intact.
- Dependency: step 6.
- Caveat: the UI must not make it look like the preset "owns" cadence once the explicit field exists.

8. Update the worker cost profile contract.
- Replace any cadence assumptions that are derived only from preset with a precedence-aware resolution path.
- Explicit tick interval from the agent should win when present.
- Cost presets may still choose the light/heavy model mix and the default thinking level.
- Runtime backoff and adaptive slowdown remain separate from the base cadence.
- Dependency: steps 1 and 6.

9. Keep runtime safety and adaptive slowdown intact.
- Preserve the behavior that the worker may slow down when idle or after failures.
- Keep the current backoff path and adaptive gating logic in the worker.
- Add tests that prove the explicit tick interval does not disable runtime slowdown.
- Dependency: step 8.

10. Define the capital semantics in the runtime/risk layer.
- Map agent capital to deployable allocation, not wallet total.
- Reuse existing notional/risk clamping patterns where possible.
- Ensure the UI copy and runtime enforcement mean the same thing.
- If the backend already has a lower-level notional cap, make sure the new capital field feeds it clearly instead of duplicating another concept.
- Dependency: step 1.

11. Add i18n keys and locale coverage.
- Add keys for all new labels, helper text, validation messages, and summary copy.
- Include copy for:
  - base cadence
  - expected cadence
  - estimated daily spend
  - slowdown caveat
  - capital semantics
  - risk guardrails
- Update locale files and i18n regression tests together.
- Dependency: steps 4, 5, and 6.

12. Add tests for the new contract.
- Backend tests should cover:
  - request validation
  - create/update persistence
  - response flattening
  - explicit tick interval precedence
  - capital and guardrail fields round-tripping correctly
- Frontend tests should cover:
  - create form rendering
  - edit form rendering
  - derived summary behavior
  - i18n lookup for the new strings
- Worker tests should cover:
  - explicit tick interval being used as the base cadence
  - runtime slowdown/backoff still applying afterward
  - preset-derived cadence only acting as fallback
- Dependency: steps 1 through 11.

13. Update supporting docs and operator copy.
- Document the difference between wallet balance and agent capital.
- Document that tick interval is the base cadence, not an exact guarantee.
- Document that runtime may still slow down when idle or after failures.
- Update any user-facing text that still implies cost presets own the cadence decision.
- Dependency: implementation completion.

## Risks and Caveats

1. The biggest risk is semantic overlap.
- If cadence, cost preset, and budget all feel like they own the same decision, the form becomes confusing.
- The plan avoids that by giving each field one clear job.

2. The second risk is inconsistent precedence.
- The server, worker, and UI must all agree that explicit tick interval wins over preset-derived cadence.
- If one layer disagrees, the derived summary will not match runtime behavior.

3. The third risk is overpromising exact timing.
- The UI must not imply the agent will tick at an exact clock rate.
- The slowdown caveat should remain visible even when the user enters an explicit interval.

4. The fourth risk is mixing capital with wallet balance.
- The UI copy should make it obvious that capital is an allocation cap, not the funding source.
- This matters especially when a wallet holds multiple agents' worth of funds.

5. `tick interval when flat` is intentionally not included in this first pass.
- If that returns later, it should default to the active cadence and only be added if the product truly needs two cadence modes.
- For now, keep the scope to one explicit base tick interval.

## Test Strategy

- Unit test the cadence helper and any precedence rules first.
- Add focused backend contract tests for create/update round-trips.
- Add form tests for create/edit coverage and i18n.
- Add at least one worker test that proves explicit cadence still allows runtime slowdown.
- Prefer narrow, deterministic tests over end-to-end-only verification for this feature.
