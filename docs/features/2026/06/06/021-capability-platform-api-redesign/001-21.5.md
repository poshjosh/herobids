## Goal

Refactor the frontend so Herobids presents itself as an agent-first platform shell whose capabilities are extended through skills, connections, bindings, and advanced capability workspaces.

After this step, the primary UX model should be:

```text
platform core -> agents -> capability cards -> capability workspaces
              -> connections / credentials as shared setup
              -> advanced capability infrastructure only when needed
```

Key outcomes:

- the default navigation and route tree center on agents, skills, connections, credentials, billing, activity, and outcomes
- users enter trading and future capability families from agents first, not from trading-first infrastructure pages
- agent creation and editing become skill-driven and capability-aware, with capability setup shown only when relevant
- mission control and core agent views are powered by agent-first read models rather than bot-shaped summaries
- execution mode is visible where users make or review agent decisions
- platform-resource pages use platform language and provider-friendly inputs instead of assuming a fixed trading-venue list
- trading infrastructure remains available for power users, but behind progressive disclosure

## Non-goals

- Do not redesign the worker/runtime here. That belongs to Step `21.4`.
- Do not replace the capability route model defined in Steps `21.1` to `21.3`.
- Do not build a generic frontend plugin framework more elaborate than what the first capability family needs.
- Do not invest in making legacy `venue_accounts` the long-term primary UX. Trading infrastructure should move toward bindings and advanced capability views.
- Do not treat Step `21.5` as the full endpoint test replacement effort. Broad route coverage belongs to Step `21.6`, though this step must still add focused validation for the new frontend flows it introduces.

## Current Code Facts

What already exists and can be reused:

- `apps/web/src/features/mission-control/MissionControlPage.tsx` already routes its primary CTA to `/agents?create=1`, derives headline counts from `agents.list()`, and uses `dashboard.activity()` only for the recent-activity panel
- `apps/web/src/features/agents/AgentsPage.tsx` already captures execution mode during creation and conditionally injects trading setup only when the selected preset includes the trading capability family
- `apps/web/src/features/agents/AgentSummaryCard.tsx` and `apps/web/src/features/agents/AgentDetailPage.tsx` already surface execution mode and capability readiness, and `apps/web/src/features/agents/AgentCapabilityPage.tsx` provides the first agent-scoped capability workspace
- `apps/web/src/features/connections/ConnectionsPage.tsx` accepts free-text providers, and `apps/web/src/features/credentials/CredentialsPage.tsx` already uses provider input with suggestions rather than a hard enum-only selector

What is still structurally wrong for Step `21.5`:

- advanced trading infrastructure still lives on legacy routes such as `/bots`, `/venue-accounts`, and `/exposure` without a bindings-first replacement path
- `apps/web/src/features/agents/AgentCapabilityPage.tsx` still routes trading setup through `/venue-accounts`, which keeps legacy infrastructure in the guided operator path
- `apps/web/src/features/credentials/CredentialsPage.tsx` still persists provider data through `venue`-shaped API fields and relies on trading-heavy secret templates
- agent creation still centers on presets rather than explicit skill selection, so the skills surface is not yet the primary configuration model
- the shell is now truthful, but not yet consolidated around a single capability-aware overview contract; capability readiness still fans out through page-level and card-level queries

This means Step `21.5` is no longer a blank-slate information-architecture rewrite. It is a partial-completion cleanup and consolidation step.

## User Stories To Drive The Refactor

Use these stories as the primary acceptance lens while implementing.

### Primary stories

1. As a new user, I can create an agent from a goal without first understanding bots, venue accounts, or trading infrastructure.
2. As a user, I can see all my agents, their status, and their execution mode from the core agent surfaces.
3. As a user, I can open mission control and trust the running counts because they reflect agent state rather than legacy bot summaries.
4. As a user, I can add credentials and connections as reusable platform resources for many providers, not just a fixed list of trading venues.
5. As a user, I can tell whether an agent is ready to use trading, and if not, what setup is missing.
6. As a user, I can navigate from the platform core into a capability such as trading through the agent that uses it.

### Power-user stories

1. As a power user, I can inspect trading bindings, provider diagnostics, and optional managed artifacts such as bots.
2. As a power user, I can reach lower-level trading infrastructure without forcing those concepts on first-run users.
3. As a power user, I can manage existing credentials, connections, and any retained advanced trading setup from the UI.

## Implementation Strategy

Treat the frontend as a platform shell with capability extensions.

Use three layers:

1. `Platform core`
   - navigation, layout, mission control, agent list/detail, skills, credentials, connections, billing, activity, outcomes
2. `Capability entry surfaces`
   - agent-scoped capability cards, readiness summaries, setup CTAs, capability-specific create/edit form sections
3. `Advanced capability workspaces`
   - trading bindings, provider diagnostics, optional bots, and any future automation or research infrastructure

The core shell should depend only on normalized platform contracts such as:

- agent summary
- execution mode
- capability readiness
- enabled capabilities
- recent activity
- outcomes

Capability-specific workspaces may depend on richer family-specific contracts such as trading bindings, positions, or provider diagnostics.

Practical rule:

- if a page answers "what is my agent doing, can it act, and what does it need?" it belongs in platform core
- if a page answers "how does trading or automation work underneath?" it belongs in a capability workspace
- if a page is mainly for troubleshooting or infrastructure control, it belongs behind advanced disclosure

## Decision Candidates To Lock Before Code

These are the specific frontend decisions the implementing agent should lock in the parent plan before making changes if they are not already recorded there.

1. Platform-core noun for trading setup lists should be `provider`, not `venue`.
   - `Platform` is too overloaded because Herobids itself is the platform.
   - `Venue` should remain available only in trading-specific advanced views when exchange semantics matter.
2. Users should navigate into capabilities from the agent detail page first.
   - global capability pages may exist, but agent-scoped entry is the primary UX.
3. Agent create/edit flows should show capability-specific config only when selected skills require that capability family.
4. Creating an agent with a trading-related skill should not require full trading setup up front.
   - allow create with `unconfigured` or `degraded` readiness and route the user into capability setup afterward.
5. Legacy `venue-accounts` should not be polished into a new primary platform concept.
   - either keep them as temporary advanced trading infrastructure or replace them with trading-binding management as the model stabilizes.

### 2. Freeze the target information architecture and route model

Before editing components, write down the target UX shape the frontend will implement.

Recommended primary route groups:

- `/mission-control`
- `/agents`
- `/agents/:agentId`
- `/skills`
- `/connections`

- `/activity`
- `/outcomes`

Recommended capability entry routes:

- `/agents/:agentId/capabilities/:family`

Recommended advanced routes:

- `/capabilities/:family/bindings`
- `/capabilities/:family/providers`
- optional family-specific diagnostics pages
- optional legacy transitional routes kept only if needed during this cut

Important guidance:

- do not keep `/instances` as a primary UX alias
- do not keep bot-first routes as the default way users enter trading
- if a route must temporarily survive for implementation convenience, make it secondary and document it as temporary in the parent plan

### 3. Define the minimal frontend capability-extension contract

Do not hard-code every capability into the agent pages forever.

Introduce a small frontend contract that lets capability families contribute:

- family ID and display label
- icon and short description
- agent-detail card renderer or card data mapper
- readiness summary renderer
- create/edit form section renderer
- primary capability actions and labels
- optional advanced routes

Keep the first version small and local to the web app.

The goal is not plugin infrastructure for its own sake. The goal is to stop the platform shell from embedding trading-specific assumptions directly into every core page.

### 4. Rebuild mission control around an agent-first read model

This is the highest-value slice because the current dashboard is visibly inconsistent.

Refactor mission control so it is driven by agent-oriented data rather than `bots` summaries.

Minimum data mission control should show:

- total agents
- active, paused, unhealthy, or stopped counts by agent state
- execution mode where relevant
- per-agent capability readiness summary
- recent activity and high-level outcomes

Implementation guidance:

- replace or reshape the legacy `dashboard.overview` contract if it cannot represent agents honestly
- do not continue translating bot summaries into "agents" in the UI
- primary CTA should lead to the real create-agent flow, not to `/instances` or bot creation
- health-strip and summary cards should reflect agent state first; capability-specific detail belongs one level deeper

This slice should directly address the current symptom where mission control can show `0 running` while an agent is actually running.

### 5. Refactor core navigation and page grouping

Once mission control has an honest read model, move the route tree and sidebar into the target platform shape.

Actions:

1. Keep agent-first surfaces prominent.
2. Add a `Skills` destination, even if the first cut is a lightweight catalog or management page.
3. Remove or demote top-level trading-first pages that do not belong in the default shell.
4. Move capability-family infrastructure under advanced sections or under explicit capability workspaces.
5. Keep `Connections` and `Credentials` in the primary manage group.

Recommended grouping:

- primary: mission control, agents, skills, activity, outcomes
- manage: connections, credentials, billing, settings
- advanced: capability infrastructure such as trading bindings, diagnostics, optional bots

`Exposure` should not remain a top-level primary page unless it is redefined in platform language.

### 6. Refactor the agent list and agent detail pages into platform-core plus capability sections

The agent detail page should become the bridge from platform core into capability workspaces.

Agent list minimum fields:

- name
- status
- execution mode
- created or updated time
- capability summary badges if useful

Agent detail minimum sections:

- objective and lifecycle
- execution mode and core constraints
- capability cards showing readiness and current setup status
- activity, outcomes, artifacts, and messages

Each capability card should support:

- readiness state
- brief setup summary
- explicit CTA such as `Configure`, `Open`, `Bind connection`, or `View trading`

The core agent page should not require users to understand bots, venue accounts, or provider-specific infrastructure before they can understand what the agent can do.

### 7. Rebuild create-agent and edit-agent flows around skills and capability requirements

This step is central to making the UX honest.

Refactor the flow so the user journey is:

1. goal and basic agent identity
2. select skills or capability-oriented presets
3. dynamically render capability setup only for the selected capability families
4. review and create

For trading-related skills, show a trading setup section only if a selected skill requires trading.

Recommended minimum trading setup fields:

- execution mode: `paper`, `shadow`, `live`
- connection or binding selection where available
- optional risk or budget guardrails
- advanced toggle for deeper trading settings

Recommended behavior:

- allow the user to skip optional trading details and create the agent anyway
- if required setup is missing, create the agent with a visible readiness state that explains what remains to be configured
- do not force venue-account selection in the core flow
- do not equate "trading agent" with "bot management" in the primary user-facing model

Also make execution mode visible in:

- agent create review
- agent list cards
- agent detail summary
- mission control where it helps users interpret behavior

### 8. Reframe credentials and connections as shared platform resources

Credentials and connections should support trading, automation, and future capabilities.

Actions:

1. rename platform-level UI copy from `venue` to `provider`
2. replace fixed-provider whitelists with free-text provider entry plus optional presets
3. allow provider-specific secret fields to remain available as optional templates, not as a hard-coded universe
4. keep secret entry and connection creation decoupled
5. add management actions for existing credentials and connections

Minimum management actions:

- credentials: inspect metadata, rename if supported, delete or revoke, and rotate path if the API shape supports it
- connections: inspect, revoke, and update display metadata if needed

Important guidance:

- do not assume only the current three trading providers exist
- keep connections reusable across capability families
- use provider-neutral copy on the core pages; family-specific terminology can return inside advanced capability views

### 9. Move trading infrastructure behind progressive disclosure

This is where the architecture principle becomes visible.

Do not remove advanced trading infrastructure entirely. Move it behind intentional entry points.

Recommended path:

1. make the default user path: `Agents -> Agent detail -> Trading capability`
2. expose advanced trading infrastructure from there, for example:
   - bindings
   - provider diagnostics
   - optional managed bots
3. keep any remaining global trading infrastructure routes in an advanced area only

Treat `Bots` as optional advanced trading artifacts, not as platform primitives.

For `venue-accounts`, choose one of two explicit paths and record the choice in the parent plan:

- temporary advanced retention: keep the page as a legacy advanced trading setup page until replaced by bindings UI
- replacement path: remove it from primary UI and replace it with trading-binding management once available

Do not silently keep both mental models alive.

### 10. Add focused tests and UAT for the new primary flows

Step `21.6` will broaden the full test model, but Step `21.5` still needs direct validation for the UX changes it introduces.

Minimum validation coverage for this step:

- router and navigation tests for the new primary IA
- mission-control tests proving counts and cards are agent-based, not bot-based
- create-agent flow tests proving trading fields appear only when trading-related skills are selected
- tests that execution mode is visible in create review and core agent surfaces
- credentials and connections tests proving provider entry is not restricted to a fixed venue list
- capability-entry tests proving users can navigate from an agent page into a capability workspace

Recommended UAT flows:

1. create a non-trading agent with no trading setup required
2. create a trading-capable agent, leave trading partially unconfigured, and verify readiness messaging
3. connect credentials and a connection, then complete trading setup from the agent capability view
4. open advanced trading infrastructure only after entering trading intentionally

If the step introduces a new agent-first dashboard or overview API, add focused integration tests for that read model now rather than waiting for Step `21.6`.

### 5. Make the agent detail page the bridge from platform core to capabilities

The agent detail page should become the default navigation bridge from platform core into capability families.

Add a normalized `Capabilities` section that can render one card per enabled or available family.

Each capability card should show:

- family label
- readiness badge
- current binding summary if present
- reasons when not ready
- primary actions or "configure" CTA
- open capability workspace CTA

For Step `21.5`, implement trading as the first real card.

Important rule:

- the agent detail page should depend on normalized capability contracts such as readiness, bindings, and actions
- it should not need to understand trading bots or venue accounts just to render the core capability summary

### 6. Refactor agent create and edit flows into skill-driven capability setup

The current create flow is too close to a trading setup form.

Change the flow shape to:

```text
goal -> skills -> capability setup (conditional) -> review -> create
```

Required behavior:

- capability setup steps are injected only when the chosen skills require that capability family
- a non-trading agent should never be shown trading-specific inputs
- a trading-capable agent should be shown a trading setup block or step only when relevant

For trading, the minimum setup block should include:

- execution mode: `paper`, `shadow`, or `live`
- connection or binding selection when available
- optional high-level risk or budget controls already supported by the agent model
- an advanced toggle for deeper provider-specific settings when needed

Do not hardwire legacy `venueAccountId` as the core setup field.

If the required trading setup is incomplete, prefer creating the agent in an honest `unconfigured` or `degraded` readiness state rather than forcing the user through unnecessary infrastructure steps during creation.

The same pattern should apply to edit flows:

- base agent fields remain in the core form
- capability-specific config panels appear only when the relevant skills are present

### 7. Surface execution mode everywhere it matters

Execution mode is currently under-exposed.

Make `paper`, `shadow`, and `live` visible in at least:

- create-agent review
- agent list cards
- agent detail header or status card
- Mission Control cards or summary rows

Rules:

- do not bury execution mode only inside edit settings
- use a compact but explicit badge or label
- if execution mode is unset or inherited, say so honestly

This is part of the core agent model, not advanced trading-only detail.

### 8. Reframe credentials and connections as general platform resources

`Connections` is already close to the target shape. `Credentials` is not.

Refactor credentials so the user can:

- enter an arbitrary provider name, with suggestions rather than a fixed whitelist
- manage existing credentials, including at least delete and any safe metadata updates already supported by the API or added locally for this step
- understand credentials as reusable auth material, not only as trading venue secrets

Recommended UX model:

- provider input should be free text with recommended options
- provider-specific secret-field presets may still exist as conveniences, but custom provider entry must remain possible
- connection creation should continue to compose a connection from optional credentials plus provider metadata

Keep `Connections` and `Credentials` close together in the platform shell because they are part of one setup journey.

### 9. Push trading infrastructure behind progressive disclosure

Do not spend this step making `Bots` and `Venue Accounts` feel like permanent top-level nouns.

Instead:

- decide whether each current surface should be removed, renamed, or demoted
- where the page must remain, reposition it as advanced trading infrastructure
- prefer capability terms such as `bindings` or `connected accounts` over preserving legacy nouns by default

If a venue-account page remains temporarily, it should not be the main entry point for trading setup. It should be reachable from:

- the trading capability workspace
- an advanced navigation section
- a direct "inspect infrastructure" link

### 10. Introduce a frontend capability-extension contract

This step should not hardcode trading logic all over the shell again.

Introduce a small composition boundary in the frontend so capability families can contribute:

- agent-detail capability cards
- conditional setup panels for create/edit flows
- advanced routes or workspace links
- family-specific status and readiness renderers

The contract can stay minimal in the first pass. It does not need a generic plugin system. It only needs enough structure so:

- the platform shell owns layout and navigation
- capability modules own their family-specific panels and advanced surfaces
- adding automation later does not require another shell rewrite

### 11. Add focused validation for the new UX shape

Step `21.6` owns broad redesign test replacement, but Step `21.5` should still add or update targeted tests for the specific flows it changes.

Minimum validation targets:

3. agent creation with non-trading skills does not show trading setup fields

Prefer a mix of:

- using `Platform` as a shared UI noun where `Provider` is the clearer and less overloaded term
- adding a large skills-management subsystem when this step only needs enough skills UX to support the new product shape
