## Goal

Refactor the worker runtime so the core agent loop becomes an orchestrator over capability-aware components instead of a monolith that owns skill resolution, prompt assembly, and family-specific context formatting directly.

After this step, the runtime model should be:

```text
skill manifests -> capability requirements -> granted bindings + readiness
               -> typed context providers -> prompt renderers -> runtime loop
```

Key outcomes:

- skills declare capability families, binding requirements, and context needs explicitly
- dedicated context providers build normalized typed blocks
- prompt renderers translate typed blocks into agent-facing prompt sections
- readiness and eligibility participate in runtime decisions, not just API reads
- context-budget and executor-budget controls are built into the composition model rather than deferred as optional tuning
- the core runtime loop stays family-agnostic, with trading as the first implemented family

## Non-goals

- Do not redesign the frontend here. That belongs to Step `21.5`.
- Do not change the public capability route contract here except for any minimum worker-supporting query additions needed to supply runtime composition data.
- Do not replace the current LLM client or the tick-loop transport model unless the runtime extraction requires a small local adjustment.
- Do not force a full direct-trading execution model in this step. Trading may still use bots or existing execution pipelines as advanced implementation details.
- Do not build an elaborate generic plugin framework before the first family proves the shape.

## Current Code Facts

The runtime architecture target is not reflected in the current worker composition yet.

What already exists and can be reused:

- `packages/domain/src/platform.ts` already defines the shared readiness contract and platform event envelope
- `apps/worker/src/agents/agent-session-manager.ts` already owns the launch path that assembles per-agent runtime config
- `apps/worker/src/index.ts` already has access to trading actor state, reconnect context, and readiness-related worker services
- the capability redesign work already introduced bindings, grants, and readiness as platform concepts

What is still structurally wrong for Step `21.4`:

- `apps/worker/src/agent.ts` still resolves skills, builds the system prompt, summarizes platform messages, formats progress, and runs the tick loop in one file
- `packages/domain/src/skills.ts` still models skills mainly as instruction strings plus `requiredTools` and stringly `contextRequirements`
- `apps/worker/src/agents/agent-session-manager.ts` still launches runtimes with only prompt, skill IDs, and tool policy, not a capability-aware runtime descriptor
- runtime authorization is still centered on tool gating, not on skill-declared family requirements plus binding readiness
- incoming worker context is still appended into the prompt as ad hoc text instead of flowing through typed context blocks and renderers
- the runtime has no explicit prompt-budget model for provider output size, tool-schema visibility, or long multi-turn tool-call history
- the current runtime still implicitly assumes trading-oriented structures such as bot status summaries and market snapshots, even though Step `21.4` says the core runtime should orchestrate rather than own family logic

This means Step `21.4` is not a prompt-tuning task. It is a composition refactor.

## Implementation Strategy

Treat Step `21.4` as a controlled extraction of runtime responsibilities, not as a full rewrite of the reasoning loop.

Preserve what already works:

- Redis stream transport
- the current tick lifecycle
- existing LLM call path
- existing worker services for trading state, readiness, and execution

Change what the runtime knows directly:

1. move family-specific context building out of `agent.ts`
2. make skills declarative enough to drive composition
3. introduce typed context contracts and renderer boundaries
4. split policy enforcement into platform baseline plus family extensions
5. wire grants, bindings, and readiness into runtime state instead of treating them as API-only concepts
6. make context-budget and executor-budget enforcement part of provider and executor composition

Use trading as the first family implementation, but do not let trading-specific wiring remain embedded in the runtime core by the end of the step.

## Step-by-Step Flow

### 1. Update the parent plan before code

Follow the implementation guide exactly.

Actions:

1. Update [000-plan.md](./000-plan.md) and mark Step `21.4` as `in progress` before writing code.
2. If any runtime contract below changes during implementation, add a Decision Log row in the parent plan before changing code.
3. If Step `21.3` is not actually complete in code, stop and do a catch-up audit instead of mixing unfinished trading-binding migration work into this step.

### 2. Freeze the runtime composition contract

Before moving files around, lock the runtime contract that Step `21.4` will implement.

Recommended minimum split:

- `runtime descriptor`: the static or slow-changing launch-time view of the agent
- `runtime state`: live per-session state accumulated from events, providers, and outcomes
- `typed context blocks`: normalized blocks built per tick or per update
- `rendered prompt sections`: presentation-layer output derived from typed blocks

The runtime descriptor should include at least:

- agent identity and goal
- resolved skill manifests
- execution mode and platform guardrails
- granted capability bindings by family
- default binding selection per family where relevant
- aggregate readiness summary or enough data to resolve it cheaply
- tool policy or capability policy baseline

Do not leave this contract implicit in environment variables and ad hoc JSON blobs. Write the types first.

### 3. Expand skill definitions from instruction bundles into declarative manifests

`packages/domain/src/skills.ts` is currently too thin for the architecture target.

Refactor `SkillDefinition` so a skill can declare more than tools and human-readable instructions.

Minimum additions to model explicitly:

- required capability families
- minimum binding requirements per family
- required typed context blocks
- prompt presentation hints or renderer selection metadata
- any family-specific action allowances that differ from plain tool exposure

Carry forward one proven runtime optimization from aitradingbot here:

- the skill manifest should remain the source of truth for tool visibility so the executor can emit only the tool schemas required by active skills, not the full global tool catalog on every turn

Keep the design minimal. The first pass does not need user-authored dynamic skill DSLs.

Practical rule:

- a skill should declare what capability context it needs
- a skill should not build that context itself
- a skill should not own provider setup flows

### 4. Introduce typed runtime context contracts

Step `21.4` needs typed context blocks that can be composed safely and tested independently.

Start with two layers:

#### Core platform envelope

Examples:

- goal and constraints
- budgets and guardrails
- recent activity
- progress summary
- granted capabilities and effective bindings
- aggregate readiness summary

#### Family-specific blocks

For the first pass, define at least one concrete family block:

- `tradingContext`

That block should be structurally normalized and should carry facts such as:

- granted default trading binding
- readiness for that binding
- current managed execution state if any
- recent outcomes or activity summaries
- market or position state where currently available through existing worker services

Do not pass raw provider payloads or random Redis message blobs directly to prompt renderers.

Also treat prompt-budget control as part of the contract, not as a later optimization pass:

- context blocks that can grow over time must expose bounded summaries rather than unbounded dumps
- the runtime should support per-block or per-provider truncation and "more available via tool" markers where appropriate
- a future global prompt budget can trim optional blocks, but Step `21.4` should already prevent obvious unbounded growth at the provider boundary

### 5. Build a context-provider registry around those typed blocks

Context providers are the center of this step.

Introduce a small provider interface in the worker layer, for example a registry keyed by block ID or capability family.

Each provider should:

1. accept the runtime descriptor plus current runtime state
2. fetch or derive the normalized facts it owns
3. return a typed context block or an explicit unavailable state

Provider metadata should also include execution-cost hints, following the aitradingbot pattern:

- cost tier such as free, cheap, or expensive
- whether the provider depends on rate-limited external APIs
- timeout or scheduling hints when the provider is slow or expensive

Important implementation guidance:

- keep providers side-effect free where possible
- prefer dedicated provider inputs over reaching into unrelated runtime globals
- make provider failures loud and observable; do not silently omit required blocks
- distinguish optional blocks from required blocks in the skill manifest
- prefetch and share upstream data needed by multiple providers so the runtime does not multiply identical DB or API reads per tick

Concrete first providers likely to extract from current code:

- progress provider from `buildProgressContext()`
- trading status or activity provider from current instance status and snapshot handling
- readiness summary provider derived from grants and binding readiness

### 6. Add prompt renderers as a separate presentation layer

The Q&A and architecture docs explicitly say prompt rendering is a presentation layer over typed context.

So the runtime should stop concatenating prompt text directly from mixed business logic.

Introduce a renderer layer that:

1. receives typed context blocks
2. emits ordered prompt sections
3. can use provider-specific wording when useful without changing the normalized data model underneath

Recommended first renderers:

- core system prompt renderer for goal, identity, tool contract, and platform guardrails
- readiness summary renderer for the small aggregated capability-status block mentioned in the Q&A
- trading renderer for family-specific trading context

The renderer layer should be the only place where provider-specific vocabulary such as provider labels or account names is reintroduced intentionally.

Prompt renderer ordering should also preserve future cacheability and token efficiency:

- stable sections first: identity, core instructions, guardrails, static skill instructions
- dynamic sections last: readiness summaries, recent activity, family-specific live context
- keep section ordering deterministic so prompt caching or prompt-diff strategies remain viable later

### 7. Rework the session-launch contract so the runtime receives a capability-aware descriptor

Today the session manager sends only a narrow `agentConfig` plus tool policy into the runtime launcher.

That is insufficient for Step `21.4`.

Update the worker launch path so the runtime starts with an explicit composition descriptor instead of reconstructing everything from prompt strings and skill IDs locally.

Minimum launch-time data to resolve before container start:

- resolved skill manifests
- active capability grants
- effective bindings per family
- readiness snapshot or enough identifiers to resolve it immediately
- default binding selection data
- prompt-budget knobs and provider-budget knobs that the runtime must enforce consistently across ticks

Possible implementation shapes:

- extend the launch payload passed into the container
- or persist a launch descriptor in Redis or DB and have the container fetch it on boot

Pick one path and document it in the parent plan before implementing. Do not split the truth across both without reason.

### 8. Add a refresh path for changing skills, grants, bindings, or readiness during a live session

Step `21.4` is incomplete if the runtime only sees capability state at process start.

Minimum runtime refresh events to support:

- skill set changed
- grant created or revoked
- default binding changed
- readiness changed in a way that affects eligibility

Implementation guidance:

- prefer one explicit runtime-config update message over ad hoc partial mutations
- update the in-memory runtime descriptor atomically
- ensure the next tick uses the new descriptor and context composition without a process restart when feasible

If a full live-refresh path is too large for the first cut, document the narrow fallback explicitly, for example restart-on-config-change. Do not leave runtime staleness as an unspoken limitation.

### 9. Refactor `apps/worker/src/agent.ts` into a thin orchestrator

Once the contracts above exist, extract the monolith.

The core runtime file should end this step owning only:

- loop lifecycle
- history management
- LLM invocation
- tool or action dispatch entry point
- coordination of providers, renderers, and policy checks

Move out of `agent.ts`:

- skill registry logic
- prompt assembly logic
- progress formatting logic
- platform-message-to-prompt formatting logic
- capability-family context derivation

The goal is not to make `agent.ts` tiny at any cost. The goal is to make it honest: orchestration, not domain composition.

### 10. Split policy enforcement into platform baseline plus family policy extensions

The architecture requires policy enforcement to be split.

Current tool gating and capability policy logic should be reorganized into:

- platform-level policy: token budget, wall-clock limits, tool availability baseline, approval requirements, generic runtime constraints
- family-level policy: capability-family action eligibility, binding-specific constraints, readiness gating, family lifecycle rules

For the first family pass, trading family policy should reuse existing trading truth where possible, such as:

- binding readiness
- agent eligibility
- existing live-execution checks
- current action semantics around managed trading flows

Do not duplicate readiness logic in the renderer or in tool handlers. One policy path should answer whether the runtime may use a capability right now.

### 11. Implement trading as the first family-specific composition chain

Step `21.4` needs one real family implementation, not just framework code.

Use trading as the proving family with the following pieces:

1. trading skill manifests declare trading capability requirements and relevant context blocks
2. a trading context provider resolves the normalized `tradingContext`
3. a trading prompt renderer formats that context for the agent
4. a trading family policy module gates use based on readiness and effective grant state

Important behavioral rule:

- bots remain optional advanced trading artifacts
- the provider may summarize bot state when it exists
- but the runtime must not treat "no bot exists" as equivalent to "trading capability does not exist"

This is where the architecture becomes real.

### 12. Replace raw inbound-message prompt stuffing with typed runtime-state updates

Today the runtime turns inbound platform messages into prompt text almost immediately.

That should change in this step.

Instead:

1. parse inbound messages into typed runtime-state updates
2. let providers consume that state when building blocks
3. let renderers decide how much of that state belongs in the prompt

Examples from the current runtime to convert:

- context snapshots
- decision accepted or rejected notifications
- execution results
- platform status updates

This preserves transport compatibility while removing prompt formatting from message parsing.

Apply the same budgeting rule to the executor loop itself:

- do not keep every old tool result at full size across long tool-calling sequences
- retain a small recent working set in full and truncate older tool results
- keep max tool turns conservative by default and skill-aware tool-definition filtering active

These are not just LLM-cost tweaks. They are required to keep the composition model viable for long-lived agents.

### 13. Write tests for composition boundaries before deleting old prompt logic

Step `21.4` will fail if tests only cover the old monolith indirectly.

Required test coverage:

1. skill manifest resolution tests
2. context-provider registry tests
3. typed context block tests for required versus optional blocks
4. prompt renderer tests for section ordering and provider-specific wording boundaries
5. runtime-descriptor launch tests in the session manager or launcher layer
6. runtime refresh tests for changed skills, grants, or readiness
7. policy tests proving ineligible or not-ready bindings are blocked even when a skill is present
8. trading composition tests proving the first family works without keeping family logic in the runtime core
9. provider-budget tests proving unbounded slices are capped or summarized predictably
10. executor-budget tests proving stale tool results are truncated and active-skill tool filtering reduces visible tool schemas

Likely test areas:

- `apps/worker/src/agent.ts` tests after extraction, or new worker runtime module tests
- `apps/worker/src/agents/agent-session-manager.test.ts`
- policy tests near `apps/worker/src/agents/capability-policy.ts`
- domain tests for expanded skill definitions

### 14. Validate narrowly after the first extraction, then validate globally

Use the validation order from the coding instructions.

Recommended validation sequence:

1. focused worker unit tests for the first extracted runtime module
2. focused session-manager or launcher tests after the descriptor contract changes
3. focused family-policy or readiness tests for the trading implementation
4. `pnpm lint`

Do not refactor the entire runtime stack before running the first narrow worker test.

## Risks To Watch

### 1. Fake decomposition

If `agent.ts` still knows how to build trading prompt sections directly, Step `21.4` is not actually done even if helper functions moved into the same file.

### 2. Skill presence confused with capability readiness

A skill saying "this agent may use trading" is not the same as having an eligible ready trading binding. Both must be checked.

### 3. Stale runtime composition

If grants or readiness can change but the runtime only sees launch-time state, agents will make decisions from stale authority data.

### 4. Raw provider payload leakage

Prompt renderers may use provider-specific wording, but typed context should still normalize structure first. Do not leak arbitrary provider JSON into prompts.

### 5. Prompt growth remains structurally unbounded

If provider output, tool-schema visibility, or old tool results can grow without caps, the composition model will degrade in both cost and reliability as agents age.

### 6. Trading remains secretly mandatory

The first family implementation must not leave trading-specific assumptions embedded in the core runtime contracts.

### 7. Over-generalizing before the first family is real

Do not build a large plugin platform with no working family implementation. Trading should prove the abstractions quickly.

## Done When

Step `21.4` is complete when all of the following are true:

- skills declare capability families, binding requirements, and typed context needs explicitly
- the runtime receives or resolves a capability-aware composition descriptor rather than reconstructing everything from prompt strings
- dedicated context providers build normalized typed blocks
- dedicated prompt renderers turn those blocks into prompt sections
- provider outputs and executor history are bounded so long-lived agents do not accumulate unbounded prompt growth
- platform-level and family-level policy enforcement are split cleanly
- readiness and eligibility affect runtime capability use directly
- trading works as the first family implementation without leaving family logic embedded in the runtime core
- the old monolithic prompt-composition path in `apps/worker/src/agent.ts` has been removed or reduced to orchestration glue
- focused runtime tests pass
- `pnpm lint` passes
