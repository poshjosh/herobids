## Goal

Finish the frontend agent-first refactor without reintroducing trading-first or bot-first assumptions.

The implementation should leave the shell in a state where:

- mission control is truthful agent-first UI, not a bot summary translator
- agent detail is the bridge into capability workspaces
- create/edit flows only reveal capability setup when relevant skills require it
- connections and credentials are treated as reusable platform resources
- trading infrastructure remains reachable, but only as advanced capability work

## What Is Already True

Before changing anything, treat the following as already completed or partially completed and preserve the working parts:

- core agent-first routes already exist in `apps/web/src/app/router.tsx`
- sidebar grouping already demotes `Bots` and `Trading setup` into `Advanced` in `apps/web/src/app/layout/Sidebar.tsx`
- `MissionControlPage.tsx` already uses `agents.list()` and `dashboard.activity()`
- `AgentSummaryCard.tsx` and `AgentDetailPage.tsx` already surface execution mode and capability readiness
- `ConnectionsPage.tsx` already accepts free-text providers
- `CredentialsPage.tsx` already moved away from a hard enum-only provider selector

The remaining work is cleanup, consolidation, and the last few honesty fixes.

## Remaining Gaps To Close

1. Mission Control still needs a dedicated empty-state regression path and should remain agent-first.
2. Agent capability pages still route trading setup through legacy `venue-accounts` surfaces.
3. Credentials still leak `venue` language and trading-heavy templates in a few places.
4. Agent create/edit flows still rely on presets more than explicit capability/skill selection.
5. The shell still lacks one fully consistent capability-aware overview pattern.
6. The new frontend tests need to be aligned with the current DOM structure and stable read models.

## Step-by-Step Flow

### 1. Reconfirm the UX contract before editing code

Start by rereading the architecture and the remaining-work inventory, then write down the exact invariants the frontend must preserve:

- the public shell is agent-first
- skills are the explicit gateway to capability families
- capabilities are exposed from agent detail first
- provider language is acceptable in the platform shell, but `venue` is advanced/trading-specific
- trading infrastructure stays available only behind progressive disclosure

If any proposed change violates one of those invariants, stop and re-scope before editing.

### 2. Restore and preserve Mission Control empty-state coverage

Work in `tests/e2e/journeys/07-mission-control-renders.spec.ts` and the Mission Control UI only if the empty-state path needs a DOM anchor adjustment.

Implement the following checks:

- new user lands on Mission Control after registration
- the empty-state copy is visible when there are no agents
- the page does not crash or fall back to an error boundary

Do not remove the agent-capability readiness flow in the same file; keep it as the second test in the same journey or a neighboring spec.

Validation checkpoint:

- Playwright listing must still show the journey files
- if the live UI copy changed, update the test to assert the actual empty-state DOM rather than weakening the coverage

### 3. Tighten capability readiness assertions to target the correct card

Refine the browser assertions in:

- `tests/e2e/journeys/01-signup-create-agent.spec.ts`
- `tests/e2e/journeys/07-mission-control-renders.spec.ts`
- `tests/e2e/journeys/08-mission-control-capability-reflects.spec.ts`

Use the current component structure instead of global text searches:

- prefer matching the readiness card or its label/value pair
- assert `Binding readiness`, `Agent eligibility`, `Effective ready`, and `Binding` together where possible
- avoid naked `.first()` matches on common values like `Ready`, `Yes`, or `No`

This step is complete when the tests clearly discriminate the intended readiness state from other page text.

### 4. Remove the last test-only dependency on private DB client internals

Use `packages/db/src/index.ts` as the supported home for database lifecycle helpers.

Implement a public helper such as `closeDatabase(db)` and keep the E2E binding seed in `tests/e2e/helpers.ts` using that helper rather than reaching into `$client` directly.

Rules:

- do not reach into private client properties from test code
- keep the helper minimal and typed
- rebuild the DB package after adding the export so the runtime package surface stays in sync

This is not a product change; it is a stability fix for the test harness.

### 5. Keep the mission-control shell agent-first and honest

Audit `apps/web/src/features/mission-control/MissionControlPage.tsx` and `apps/web/src/features/agents/AgentSummaryCard.tsx`.

Check for these conditions:

- the page title and CTA remain agent-oriented
- counts come from agent truth, not bot-shaped summaries
- the empty state explains that agents are created from goals
- readiness in summary cards is drawn from the normalized capability contracts already in place

Only change these components if the empty state or summary copy still implies a bot-first mental model.

### 6. Make agent detail the bridge into capability workspaces

Review `apps/web/src/features/agents/AgentDetailPage.tsx` and `apps/web/src/features/agents/AgentCapabilityPage.tsx` together.

The desired state is:

- agent detail shows a normalized capabilities section
- each capability card exposes readiness, summary, and a clear open/configure CTA
- the trading capability page remains the first real capability workspace
- trading setup actions do not force users into `venue-accounts` as a primary path

If `AgentCapabilityPage.tsx` still sends the user into `venue-accounts`, decide whether the page should:

- link to a clearly labeled advanced surface, or
- point to a better capability-appropriate setup path already present in the UI

Document the choice in the parent plan if it is a lasting behavior.

### 7. Rework create/edit flows so skills drive capability setup

Focus on `apps/web/src/features/agents/AgentsPage.tsx` and `apps/web/src/features/agents/EditAgentModal.tsx`.

The target journey is:

1. goal and agent identity
2. skills or capability-oriented preset selection
3. conditional capability setup only when the selected skills require it
4. review
5. create or save

Behavior requirements:

- non-trading agents should not see trading-only inputs
- trading-capable agents should see trading setup only when relevant
- execution mode should stay visible in the review path and list/detail surfaces
- if setup is incomplete, creation should still be possible with honest readiness state

Use the smallest possible form change that makes the UX truthful. Do not introduce a framework for arbitrary capability plugins.

### 8. Keep credentials and connections provider-first

Review `apps/web/src/features/credentials/CredentialsPage.tsx` and `apps/web/src/features/connections/ConnectionsPage.tsx`.

The key refactor is copy and shape:

- use `provider` language in core platform UI
- keep provider entry open-ended with suggestions instead of a fixed venue list
- keep secret templates optional and secondary
- avoid making the platform shell feel trading-specific

If backend field names still use `venue`, the UI may still map to them internally, but the visible product language should stay provider-first.

### 9. Demote or relabel advanced trading infrastructure instead of polishing it into core

If any remaining UI still elevates `Bots`, `Venue accounts`, or `Exposure`, keep it behind progressive disclosure.

Preferred posture:

- the default path is `Agents -> Agent detail -> Trading capability`
- advanced infrastructure is reachable from there
- legacy routes remain secondary only if needed for continuity during this cut

Do not invest in making advanced trading pages feel like the new primary shell.

### 10. Finish the skills surface only where it supports the core journey

If `apps/web/src/features/skills/SkillsPage.tsx` still feels disconnected from the agent-first story, update only the parts that help the new create/edit flow.

The skills page should support:

- discovering which skills unlock which capability families
- understanding that capability setup is conditional, not universal

Do not overbuild a plugin framework. The page just needs to support the current agent-first configuration model.

### 11. Update or add focused validation after every behavior change

Use the narrowest executable validation that can falsify the current change:

- `pnpm lint` for TypeScript and package-level contract changes
- `pnpm --dir tests/e2e exec playwright test ... --list` for journey syntax and discovery
- targeted Playwright execution when the browser flow itself changes

If a change touches both the DB package and the E2E helper layer, rebuild the package before rerunning Playwright.

### 12. Record the remaining-work outcome in the parent plan if the scope changes

If implementation reveals a real scope change, write it into `000-plan.md` before continuing.

Examples of scope changes that should be documented:

- choosing to retain a legacy advanced page longer than planned
- changing the navigation destination for trading setup
- introducing a dedicated capability-aware overview contract

Keep the plan honest; do not silently absorb deviations.

## Suggested Execution Order

If an LLM agent needs a concrete order, use this sequence:

1. restore Mission Control empty-state coverage
2. tighten the readiness assertions in the browser journeys
3. remove the private DB-client escape hatch from the E2E helper
4. confirm the shell still reads as agent-first in mission control and agent detail
5. refactor create/edit flows to make skills drive capability setup
6. finish provider-first credentials and connections copy
7. demote or relabel any remaining advanced trading surfaces
8. validate with lint and the affected Playwright checks

## Exit Criteria

Treat Step `21.5` remaining work as complete only when:

- Mission Control has empty-state and populated-state browser coverage
- capability readiness assertions are stable and tied to the intended UI card
- E2E helper code no longer depends on private DB client internals
- the shell remains visibly agent-first
- create/edit flows do not force trading setup for non-relevant skills
- credentials and connections stay provider-first in the platform shell
- advanced trading infrastructure remains secondary
- `pnpm lint` passes
