## Goal

Finish the trading-family migration that Step `21.2` intentionally left as a bridge.

After this step, trading should no longer be modeled publicly or internally around `venue_accounts` plus mandatory `bots`.

Instead, the canonical model should be:

```text
credential -> connection -> trading binding -> capability grant -> optional bot
```

Key outcomes:

- `venue_accounts` stop being the canonical public trading resource
- trading bindings become the real family-specific execution target
- grants point to trading bindings, not raw connections
- bots become optional advanced trading artifacts rather than the required product primitive
- agent-scoped trading routes tell the truth about real trading bindings instead of projecting old nouns into new names

## Non-goals

- Do not redesign the frontend here. That belongs to Step `21.5`.
- Do not broaden into the runtime refactor planned for Step `21.4` beyond the minimum wiring needed to stop depending on `venue_accounts` as the core trading noun.
- Do not add backward-compatibility routes, aliases, or parallel models that keep both `venue_accounts` and trading bindings alive as equal public concepts.
- Do not invent a second generic binding framework before trading proves the shape. Keep the first implementation concrete and tight.

## Current Code Facts

The codebase is already halfway through the redesign, but the trading model is still a bridge.

What already moved in the right direction:

- `apps/api/src/routes/capabilities/index.ts` registers the capability namespace as a primary public surface
- `apps/api/src/routes/capabilities/trading.ts` exposes family-level and agent-scoped trading capability routes
- `packages/db/src/schema/connections.ts` and `packages/db/src/schema/capability-grants.ts` already model shared platform connections and capability-scoped grants

What is still structurally wrong for Step `21.3`:

- `apps/api/src/routes/capabilities/trading.ts` still projects raw `connections` as if they were trading bindings
- the same file still returns grant IDs as `bindingId` values on agent-scoped binding reads
- `packages/db/src/schema/venue-accounts.ts` still holds the real trading account resource, with trading-specific metadata and credential linkage
- `packages/db/src/schema/bots.ts` still requires `venueAccountId`, so bots remain coupled to the old noun
- `apps/api/src/schemas.ts` still treats `venueAccountId` as the canonical bot input
- `apps/worker/src/index.ts`, `apps/worker/src/trading-actor.ts`, and `apps/worker/src/live-gate.ts` still resolve execution and credential loading through `venueAccountId`
- agent trading state in `apps/api/src/routes/capabilities/trading.ts` is still aggregated by finding bot actors created by the agent
- `apps/api/src/index.ts` still keeps `accounts.ts` and `bots.ts` alive as advanced routes because the deeper resource migration has not happened yet

This means Step `21.2` changed the route shape, but Step `21.3` still needs to change the actual trading resource model.

## Implementation Strategy

Treat Step `21.3` as the model-correction step.

Do not keep layering projections on top of `venue_accounts` and `bots`.

Instead:

1. introduce a real trading-binding persistence model
2. migrate grants so the effective grant points at the trading binding
3. move bots behind that binding model as optional managed artifacts
4. update capability routes and services to read from the new model directly
5. remove or demote old `venue_accounts` assumptions so Step `21.4` can focus on runtime composition rather than cleanup debt

## Step-by-Step Flow

### 1. Update the parent plan before code

Follow the implementation guide exactly.

Actions:

1. Update [000-plan.md](./000-plan.md) and mark Step `21.3` as `in progress` before writing code.
2. If any design choice below changes during implementation, write that into the parent plan Decision Log before changing code.
3. If Step `21.2` is not actually complete in code, stop and do a catch-up audit instead of silently blending unfinished Step `21.2` work into Step `21.3`.

### 2. Freeze the canonical trading resource model

Before editing tables or handlers, lock the target model in code comments or a short Decision Log entry.

The first complete trading-family model should be:

- `connection`: user-owned external linkage
- `trading binding`: family-specific trading execution target derived from a connection
- `capability grant`: agent authority to use that trading binding
- `bot`: optional managed runtime artifact attached to a trading binding when continuous managed execution is desired

Required invariants:

1. a trading binding is the effective grant target
2. a trading binding traces back to exactly one connection
3. a connection may produce one or more trading bindings
4. a bot never replaces the binding as the source of authority
5. agent-scoped capability routes must use binding language truthfully, not as a projection label over connections or grants

Decide explicitly before coding:

- whether the initial trading family allows multiple bindings per connection only when provider/account structure requires it
- where the per-agent default trading binding lives if an agent has multiple trading grants
- whether the default binding is represented on the grant, in separate family state, or derived deterministically

Do not leave these as implicit handler behavior.

### 3. Introduce a real trading-binding persistence model

Step `21.3` needs a real family-specific binding table or an equivalent canonical replacement for `venue_accounts`.

Recommended direction:

- create `packages/db/src/schema/trading-bindings.ts`
- keep the schema trading-specific rather than prematurely generic
- back it with a Drizzle migration that maps current `venue_accounts` data into the new table

Recommended minimum fields:

- `id`
- `userId`
- `connectionId`
- `provider`
- `label`
- `bindingRef` or provider account reference
- `status`
- `bindingProfile` or normalized trading capability metadata
- `sourceVenueAccountId` only if needed temporarily for migration traceability
- timestamps

Model rules:

- provider-specific account metadata belongs on the binding, not on the connection
- connection stays capability-agnostic
- credential traceability comes through the connection, not by duplicating secret ownership on the binding
- readiness detail can be derived from binding plus grant state, but the binding should carry the provider/account facts needed to compute that truthfully

Do not simply rename `venue_accounts` in the API while leaving the old table semantics untouched. The schema should reflect the new capability-family role.

### 4. Migrate grants from connection-scoped to binding-scoped authority

This is the core correction that Step `21.3` must make.

Today, `capability_grants` still point to `connection_id`. That contradicts the architecture decision that effective grants point to family-specific bindings.

Recommended direction:

1. change the grant model so the canonical foreign key points to a capability binding
2. for trading, backfill existing grants from `(agent, connection, family)` to `(agent, tradingBinding, family)`
3. keep connection traceability on the trading binding itself, not as the effective grant target

Implementation choices to make explicitly:

- either rename `connectionId` to a generic `bindingId` now
- or introduce `bindingId` first, backfill it, and remove `connectionId` in the same step if the migration is clean

Because the platform is not live and backward compatibility is explicitly rejected, prefer the simpler end state over a long-lived dual-column bridge.

Also update:

- grant services
- grant audit reads
- readiness aggregation
- capability route handlers
- tests that currently assume grant IDs or connection IDs double as trading binding IDs

### 5. Rewire bots onto trading bindings and make them secondary

Bots should remain available, but they should stop anchoring the trading model.

Recommended direction:

1. replace `bots.venueAccountId` with `bots.tradingBindingId`
2. update bot creation, read, and lifecycle services to resolve trading execution context through the binding
3. keep bots as an advanced managed construct for users or systems that explicitly want them
4. remove any assumption that an agent must have a bot in order to have trading capability state

Important constraint:

- if parts of the worker still require a bot runtime for managed trading loops, that is acceptable in this step
- but the bot must be treated as an internal or advanced artifact, not the public authority model

Public contract rule:

- agent trading capability routes should not require callers to understand `botId` in order to understand bindings, readiness, or authorization

### 6. Replace trading capability route projections with real binding-backed reads

Once real trading bindings exist, remove the Step `21.2` bridge behavior from `apps/api/src/routes/capabilities/trading.ts`.

Concrete route corrections:

- `GET /capabilities/trading/bindings` must read trading bindings, not raw connections
- `GET /agents/:agentId/capabilities/trading/bindings` must return granted trading bindings, not grants pretending to be bindings
- binding inspection routes must key on real binding IDs
- bind and unbind actions must accept real trading binding identifiers
- readiness must report the granted binding ID, not a grant ID or a connection ID masquerading as one

Also tighten the response shape so it exposes binding truth clearly, for example:

- binding identity
- provider
- label
- provider account reference
- binding profile or capabilities
- connection provenance
- grant status
- readiness summary

The API should make it obvious that trading bindings are the execution targets derived from connections.

### 7. Reframe trading setup flows around bindings rather than venue accounts

The resource migration is incomplete if setup flows still revolve around `/venue-accounts`.

Required direction:

1. move the canonical setup path to the trading capability surface
2. treat binding provisioning as the capability-family operation that turns a connection into a usable trading target
3. keep advanced provider diagnostics separate from the public binding model

Practical implementation options:

- create trading bindings eagerly when the user configures the trading capability against a connection
- or create them through an explicit trading-family action endpoint such as bind or provision

What matters is the final shape:

- the caller thinks in connections, trading bindings, grants, and agent capability actions
- the caller does not have to think in `venue_accounts`

If `apps/api/src/routes/accounts.ts` remains temporarily during the transition, it should be clearly demoted and scheduled for removal inside this same step rather than left as a shadow primary model.

### 8. Reframe agent trading state, activity, and outcomes away from bot-first aggregation

Step `21.2` still computes agent trading state by locating agent-created bots and aggregating their records.

Step `21.3` should move the mental model one layer up.

Recommended direction:

1. define how agent trading state is derived from granted bindings plus execution artifacts
2. prefer agent-scoped trading views that are binding-aware and execution-mode-aware
3. keep bot-derived aggregation only as an implementation detail where historical records still use bot actors

Practical rule:

- if fills, positions, or outcomes still reference bot actors, wrap that in extracted trading capability query services
- do not leave that bot-centric derivation embedded directly in the public capability route handlers

The route handler should answer agent-scoped trading questions. It should not expose how many internal bot records were traversed to answer them.

### 9. Retire or sharply demote `venue_accounts` as a public concept

The plan says trading bindings are the new model. That means `venue_accounts` cannot remain a parallel first-class public noun.

Required cleanup:

- remove `venue_accounts` from the primary route model
- stop using `venueAccountId` in new API schemas and route contracts
- move any remaining provider-specific inspection or migration helpers behind advanced or internal-only surfaces
- update tests and fixtures so they create trading bindings rather than venue accounts as the canonical trading resource

Because backward compatibility is explicitly rejected, do not keep `/venue-accounts` around just to avoid touching tests.

### 10. Write the new tests first, then replace the old assumptions

Step `21.3` changes schema, authority, and route truth. That needs explicit regression coverage.

Required test coverage:

1. DB migration coverage for trading bindings and grant backfill
2. route tests proving `GET /capabilities/trading/bindings` returns real trading bindings
3. route tests proving agent-scoped trading bindings are real binding records, not projected grants or connections
4. bind and unbind action tests using binding IDs
5. readiness tests proving `bindingId` refers to the real trading binding
6. bot tests proving bots attach to `tradingBindingId` rather than `venueAccountId`
7. agent trading state and outcomes tests proving the public capability layer still works without exposing bot-first assumptions
8. tests proving old `venue_accounts` assumptions are gone or explicitly demoted

Likely test areas:

- `apps/api/src/routes/capabilities/trading.test.ts`
- `apps/api/src/routes/bots.test.ts`
- `packages/db/src/*integration.test.ts`
- any route tests still creating `venue_accounts` as the canonical prerequisite for trading capability usage

### 11. Validate narrowly after each model slice, then run global checks

Use the validation order from the coding instructions.

Recommended validation sequence:

1. migration or schema-scoped DB tests
2. targeted API route tests for trading capability bindings and actions
3. targeted bot tests after switching from `venueAccountId` to `tradingBindingId`
4. `pnpm lint`

Do not make the entire schema migration, grant rewrite, bot rewrite, and route rewrite before running the first focused test.

## Risks To Watch

### 1. Dual truth between connections and bindings

If trading bindings are introduced but routes continue to treat connections as interchangeable with bindings, the redesign remains logically broken.

### 2. Grant migration stops halfway

If `capability_grants` still point at connections after this step, the architecture contract is still not true and future capability families will inherit the wrong model.

### 3. Bots stay secretly mandatory

If the API still requires a bot to represent basic trading capability state, then bots are still the real primitive even if the docs say otherwise.

### 4. Route contracts lie about binding IDs

This is already happening in the bridge implementation. Step `21.3` must remove it completely.

### 5. Historical trading data remains hard-coded to bot actors

If fills, positions, and outcomes still depend on bot actor IDs, isolate that in capability query services so Step `21.4` does not inherit route-level bot coupling.

### 6. Over-generalizing too early

Do not build a universal cross-family binding engine during the first true family migration. Trading should prove the shape with the smallest honest abstraction.

## Done When

Step `21.3` is complete when all of the following are true:

- trading bindings exist as real persisted trading-family resources
- `venue_accounts` are no longer the canonical public trading resource
- capability grants point to trading bindings rather than raw connections
- bots point to trading bindings and are clearly secondary or advanced constructs
- family-level and agent-scoped trading capability routes read from real bindings
- readiness and bind or unbind flows use real binding IDs
- agent trading state, activity, and outcomes no longer expose bot-first resource assumptions in the public route layer
- tests cover the new binding-backed model
- `pnpm lint` passes
