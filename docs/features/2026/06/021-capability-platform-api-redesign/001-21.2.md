## Goal

Implement the canonical capability route model in the API layer so the public surface becomes:

```text
/capabilities/:family/...
/agents/:agentId/capabilities/:family/...
```

This step is about route shape, registration, and operational entry points.

It is not the full trading-binding migration. Step 21.3 will finish the deeper trading resource reframing.

## Non-goals

- Do not redesign the frontend here. That belongs to Step 21.5.
- Do not invent the final trading binding model here. Step 21.3 will move `venue_accounts` to trading bindings.
- Do not add backward-compatibility aliases or shims.
- Do not widen into worker/runtime refactors beyond what route handlers need to call existing services.

## Current Code Facts

The current API is already partway through the redesign, but the route model is split.

What already matches the target direction:

- `apps/api/src/routes/readiness.ts` already exposes `/agents/:agentId/capabilities/:family/readiness`
- `apps/api/src/routes/connections.ts` already exposes platform-level `/connections`
- `apps/api/src/routes/grants.ts` already models capability-scoped grants, even though the path is still `/agents/:agentId/grants`

What still reflects the old trading-first shape:

- `apps/api/src/index.ts` still registers `bots`, `venue-accounts`, `live-status`, views, reconciliation, and exports as primary route modules
- `apps/api/src/routes/accounts.ts` exposes `/venue-accounts`
- `apps/api/src/routes/bots.ts` exposes `/bots`, `/bots/:id/start`, `/bots/:id/stop`, `/bots/:id/config`, and bot-centric reads
- `apps/api/src/routes/live-status.ts` still exposes `/instances/:id/live-status` and `/instances/:id/live-readiness`
- `apps/api/src/routes/views.ts`, `apps/api/src/routes/reconciliation.ts`, and `apps/api/src/routes/exports.ts` still expose trading-first or bot-first reads
- `apps/api/src/routes/agents.ts` still exposes agent-to-bot routes like `/agents/:id/bots`

The practical consequence is that Step 21.2 is not greenfield work. It is a consolidation step:

1. add the canonical capability route registration model
2. move the primary operational surface under capability routes
3. remove or demote conflicting trading-first assumptions

## Implementation Strategy

Treat Step 21.2 as a hard-cut route redesign, but do not block on the full Step 21.3 binding migration.

That means:

- the public route model must switch now
- trading can use temporary projections over current `bots`, `venue_accounts`, grants, readiness, journal, and export data
- those temporary projections must be clearly isolated so Step 21.3 can replace them cleanly

## 2. Freeze the Step 21.2 route contract

Before writing handlers, lock the exact public contract for the first capability family: `trading`.

Minimum contract to implement now:

### Family-level routes

```text
GET /capabilities
GET /capabilities/trading
GET /capabilities/trading/providers
GET /capabilities/trading/bindings
```

### Agent-scoped routes

```text
GET  /agents/:agentId/capabilities/trading
GET  /agents/:agentId/capabilities/trading/state
GET  /agents/:agentId/capabilities/trading/readiness
GET  /agents/:agentId/capabilities/trading/bindings
GET  /agents/:agentId/capabilities/trading/activity
GET  /agents/:agentId/capabilities/trading/outcomes
POST /agents/:agentId/capabilities/trading/actions/:action
```

Contract rules:

- reads stay resource-oriented
- every mutation goes through `/actions/:action`
- no new bot-first or venue-first public endpoints may be added
- no compatibility aliases such as keeping both `/bots/:id/start` and `/agents/:agentId/capabilities/trading/actions/...`

Important implementation constraint:

- do not fake a final direct-execution contract if the backend still depends on current bot lifecycle primitives
- expose only the action names that the system can support honestly in this step
- if the first supported actions are wrappers around current start, stop, pause, or resume behavior, make that explicit in code and tests

## 3. Add a capability route registration model

Step 21.2 explicitly calls for a route registration model, not just a new pile of handlers.

Create a small routing abstraction in the API layer, for example:

- `apps/api/src/routes/capabilities.ts`, or
- `apps/api/src/routes/capabilities/registry.ts` plus family modules under `apps/api/src/routes/capabilities/`

The abstraction should do three things:

1. register shared capability-family entry points such as `/capabilities` and `/capabilities/:family`
2. delegate family-specific routes to a registrar for `trading`
3. keep `apps/api/src/index.ts` from becoming the place where route semantics are hard-coded

Recommended shape:

- one shared registrar for the namespace
- one family-specific registrar for trading
- thin handlers that call extracted query/action services rather than duplicating SQL across old and new route files

Do not build an elaborate plugin system. Step 21.2 only needs the smallest abstraction that supports `trading` now and additional families later.

## 4. Register the canonical namespace in the API entrypoint

Update `apps/api/src/index.ts` so the primary route registration reflects the new model.

Concrete goals:

1. register the new capability route module
2. stop treating bot-first and venue-first route modules as the primary public surface
3. keep platform primitives like `/connections`, `/credentials`, `/skills`, `/billing`, `/events`, and `/admin` at the root

This is the pivot point for the hard cut. After this change, the API entrypoint should read like an agent-first platform API, not a trading-first API with add-ons.

## 5. Implement family-level trading routes as projections over current data

Use the current persistence model as a bridge rather than waiting for Step 21.3.

Expected behavior for the initial trading family routes:

- `GET /capabilities` returns the available capability families and high-level metadata
- `GET /capabilities/trading` returns trading family metadata, readiness summary rules, and supported actions
- `GET /capabilities/trading/providers` returns the currently supported trading providers/platforms derived from existing trading infrastructure
- `GET /capabilities/trading/bindings` returns the current user-owned trading-capable resources projected into the new capability model

For this step, it is acceptable for `bindings` to be a temporary projection over:

- current connections
- current grants
- current `venue_accounts`

But the response shape must be capability-oriented, not venue-account-oriented.

That means the user should not need to understand the old storage nouns to consume the route.

## 6. Implement agent-scoped trading routes as the primary operational surface

These routes are the core of Step 21.2.

Expected behavior:

- `/agents/:agentId/capabilities/trading` returns the top-level trading capability view for the agent
- `/state` returns the current agent-scoped trading state
- `/readiness` returns the canonical readiness contract already introduced in Step 21.1
- `/bindings` returns the agent's effective trading bindings or grants in the new route shape
- `/activity` returns the trading activity stream for the agent
- `/outcomes` returns trading outcomes and summaries for the agent
- `/actions/:action` is the only mutating entry point

Implementation guidance:

1. Reuse the existing readiness logic instead of rewriting it.
2. Extract reusable query services from `bots.ts`, `live-status.ts`, `views.ts`, `reconciliation.ts`, `exports.ts`, and `agents.ts` where needed.
3. Scope everything by authenticated user and agent ownership first, then capability family.
4. Prefer agent-scoped aggregation over bot-scoped reads.
5. Where current data is only available through bots, expose agent-level aggregation rather than leaking bot-first paths back into the public contract.

The route should tell the truth about today's backend shape while still conforming to the new public API.

## 7. Move grant and readiness access under the capability surface

`readiness.ts` is already on the correct path family, but it should become part of the new capability route registration model rather than standing apart as a special case.

`grants.ts` still exposes `/agents/:agentId/grants`.

For Step 21.2, fold grant access into the capability route surface so the operational model stays coherent.

Recommended direction:

- agent-scoped binding or grant inspection should live under `/agents/:agentId/capabilities/:family/...`
- the handler may still call the current grant service internally
- do not leave grant lifecycle endpoints on a parallel non-capability path if they are part of day-to-day capability use

If the final public noun chosen here is `bindings` rather than `grants`, document that explicitly in the parent plan decision log before implementing.

## 8. Remove or demote conflicting trading-first route assumptions

Step 21.2 does not require deleting every trading-specific helper immediately, but it does require removing route assumptions that conflict with the new model.

Use this rule:

- if a route defines the primary public operational path, it must move now
- if a route is still needed as a temporary internal bridge, isolate it behind extracted services and stop treating it as the canonical public contract

Targets to review directly:

- `apps/api/src/routes/accounts.ts`
- `apps/api/src/routes/bots.ts`
- `apps/api/src/routes/live-status.ts`
- `apps/api/src/routes/views.ts`
- `apps/api/src/routes/reconciliation.ts`
- `apps/api/src/routes/exports.ts`
- `apps/api/src/routes/agents.ts`

Expected result:

- no primary trading workflow requires the caller to start from `/venue-accounts`, `/bots`, or `/instances`
- no mutating trading workflow depends on resource-specific verbs outside `/actions/:action`
- any remaining advanced trading routes are clearly secondary and ready to be absorbed or replaced in Step 21.3

## 9. Write the new tests first, then replace the old route assumptions

The roadmap says stub-first plus integration tests.

So before completing the implementation, add or update failing tests for the new contract.

Required test coverage:

1. route registration tests for the canonical trading capability namespace
2. ownership and 404 tests for agent-scoped capability routes
3. readiness tests through the canonical capability path
4. bindings or grants tests through the new capability path
5. activity and outcomes tests for agent-scoped trading reads
6. explicit action-endpoint tests proving mutations happen only through `/actions/:action`
7. tests proving conflicting old assumptions are gone or no longer canonical

Likely test locations:

- `apps/api/src/routes/*.test.ts`
- `apps/api/src/__tests__/functional/`

Do not leave the system in a state where the new routes exist but the test suite still treats `/bots`, `/venue-accounts`, or `/instances` as the primary contract.

## 10. Validate narrowly, then validate globally

After the first substantive route edit, run a focused validation step immediately.

Recommended order:

1. targeted route tests for the touched capability module
2. targeted functional tests for agent-scoped capability endpoints
3. `pnpm lint`

If a focused route test fails, fix that slice before widening further.

## Risks To Watch

### 1. Connection vs binding confusion

Step 21.1 grants still point at current connection records, while the architecture wants grants to point at capability-specific bindings.

Step 21.2 should not solve that with ad hoc route naming. Use a projection layer now and leave the true binding migration for Step 21.3.

### 2. Duplicated query logic

If new capability routes copy SQL from `bots.ts`, `exports.ts`, `views.ts`, and `live-status.ts`, Step 21.3 will become cleanup debt.

Extract shared services instead.

### 3. Dishonest action contracts

Do not expose an `execute` action unless the backend can really perform the semantics that name implies.

If current behavior is closer to start, stop, pause, or resume of an existing managed trading flow, use those action names until Step 21.3 changes the execution model.

### 4. Partial hard cut

The biggest failure mode is ending with both route models half alive.

The API may still use bridge internals, but the public contract, tests, and entrypoint registration must clearly pick one model.

## Done When

Step 21.2 is complete when all of the following are true:

- the API entrypoint registers the capability namespace as the primary route model
- trading has family-level routes under `/capabilities/trading/...`
- trading has agent-scoped operational routes under `/agents/:agentId/capabilities/trading/...`
- readiness, bindings or grants, activity, outcomes, and actions are reachable through the canonical capability path
- mutating operations use explicit `/actions/:action` routes
- conflicting trading-first route assumptions have been removed or clearly demoted as temporary internal bridges
- route tests and functional tests cover the new contract
- `pnpm lint` passes
