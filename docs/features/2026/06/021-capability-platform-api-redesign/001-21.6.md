## Goal

Replace trading-first test assumptions with capability-model coverage that proves the redesigned platform works through:

```text
platform primitives -> capability routes -> grant/readiness lifecycle -> shared events
                   -> agent-first UI journeys -> execution entry points
```

After this step:

- API integration tests prove the new platform resources and capability routes against the real app wiring rather than only mocked route handlers
- grant, binding, readiness, and revocation semantics are covered as lifecycle behavior, not just isolated helper calls
- shared event-envelope behavior is covered on the WebSocket surface used by clients
- UAT journeys follow the new agent-first flow for capability enablement and execution
- obsolete tests that still encode trading-first public assumptions are deleted or rewritten so the suite stops protecting the wrong product shape

## Non-goals

- Do not redesign the API here. Step `21.6` validates the model settled by Steps `21.1` to `21.5`.
- Do not add real-provider integration tests that require live exchange or third-party credentials.
- Do not keep legacy tests purely for comfort if they enforce route shapes or UX assumptions the redesign explicitly rejected.
- Do not collapse all testing into one giant end-to-end flow. Keep route integration, lifecycle integration, and browser UAT distinct.

What already exists:

- route-level tests exist for the new capability model, including `apps/api/src/routes/connections.test.ts`, `apps/api/src/routes/capabilities/trading.test.ts`, `apps/api/src/routes/events.test.ts`, and `apps/api/src/grant-service.test.ts`

- browser journeys already exist under `tests/e2e/journeys/`
- `tests/e2e/helpers.ts` already supports the agent-first create and bind flow with helpers such as `createAgent(...)`, `createConnection(...)`, and `bindTradingCapability(...)`
- the main test runner is `scripts/shell/tests/run-all-tests.sh`

What is still structurally wrong for Step `21.6`:

- most of the capability-route tests are still handler-level tests with mocked DB chains, so they do not prove the real API wiring, persistence semantics, or cross-route lifecycle behavior
- `apps/api/src/__tests__/functional/helpers.ts` still does not register `/events` or credentials routes, so the functional harness cannot yet prove the full shared-event and platform-resource surface end to end
- the browser flow is partially aligned, but it still relies on direct trading-binding seeding because the public app does not yet expose a binding-creation surface
- there are still many tests elsewhere in the repo whose assertions are rooted in `/bots`, venue-account-first setup, or trading-first API framing; Step `21.6` must decide case by case whether each one stays as a valid advanced-trading test or is now protecting the wrong public model

This means Step `21.6` is not a test-count exercise. It is a replacement of the suite's public truth.

## Test Strategy

Use three layers and keep each layer honest about what it proves.

### 1. API integration tests

Purpose:

- verify the real Fastify app wiring
- verify DB-backed lifecycle behavior for platform primitives and capability routes
- replace fragile mocked-route assumptions for the redesigned public API

Primary surface:

- `apps/api/src/__tests__/functional/`

### 2. WebSocket and event-model tests

Purpose:

- verify the shared event envelope on the actual `/events` surface
- verify user scoping and capability metadata propagation

Primary surface:

- extend `apps/api/src/routes/events.test.ts` or add a focused functional-style event integration test if mocked coverage becomes too weak

### 3. Agent-first UAT journeys

Purpose:

- verify the main user flow from agent creation through capability setup and execution
- catch product regressions that route-level API tests cannot see

Primary surface:

- `tests/e2e/journeys/`

Practical rule:

- use mocked route tests for narrow local branching only
- use functional API tests for route contracts and lifecycle semantics
- use Playwright for the product journeys the user actually experiences

## Coverage Model To Implement

The minimum Step `21.6` matrix should cover the redesign claims directly.

### Platform primitives

- connections: create, list, get, revoke
- grants: create, revoke, audit visibility, duplicate-active protection
- readiness: `unconfigured`, `ready`, `degraded`, `revoked`, and ineligible cases where the agent cannot currently use the binding

### Capability routes

- family-level route coverage under `/capabilities/:family/...`
- agent-scoped route coverage under `/agents/:agentId/capabilities/:family/...`
- explicit action endpoints such as `bind`, `unbind`, `start`, `stop`, `pause`, and `resume` where the family exposes them

### Shared event model

- WebSocket subscription remains user-scoped
- payloads use the shared `PlatformEventEnvelope` shape
- capability metadata such as `capabilityFamily` and `bindingId` is preserved when present

### UAT flows

- create an agent through the agent-first flow
- observe missing capability readiness rather than being blocked by trading-first setup
- add or select reusable platform resources needed for the capability
- grant or bind the capability to the agent
- observe readiness transition to usable state
- execute the primary capability action from the agent surface
- confirm mission-control and agent-detail surfaces reflect the new truth

## Step-by-Step Flow

### 1. Update the parent plan before code

Follow the implementation guide exactly.

Actions:

1. Update [000-plan.md](./000-plan.md) and mark Step `21.6` as `in progress` before editing tests.
2. If this has not already been recorded in the parent plan, add a Decision Log entry standardizing UAT on the existing Playwright journeys and `scripts/shell/tests/run-all-tests.sh` rather than inventing a new `run-uat.sh`.
3. If the existing code is not actually complete enough to support the target routes, stop and record the blocker instead of hiding missing implementation behind skipped tests.

### 2. Audit the current suite and classify tests into keep, rewrite, or delete

Start with the tests already closest to the redesign:

- `apps/api/src/routes/connections.test.ts`
- `apps/api/src/routes/capabilities/trading.test.ts`
- `apps/api/src/routes/events.test.ts`
- `apps/api/src/grant-service.test.ts`
- `apps/api/src/__tests__/functional/`
- `tests/e2e/journeys/`

For each test file, decide one of three outcomes:

- `keep` if it still validates a real behavior that survives the redesign
- `rewrite` if the behavior is still valid but the nouns, route shape, or assertions are obsolete
- `delete` if the test protects a rejected public assumption

Do not delete coverage before the replacement test exists.

### 3. Upgrade the functional test harness to include the new platform and capability routes

The first hard dependency for Step `21.6` is a realistic app builder.

Update `apps/api/src/__tests__/functional/helpers.ts` so the functional app registers the remaining redesigned route surfaces needed by this step, including at least:

- events routes
- credentials routes
- any additional grant/readiness support routes not yet covered through the current capability registration

Preserve the current auth and DB setup pattern. Do not create a second competing functional harness unless there is a concrete blocker.

### 4. Write failing API integration tests for the new route model first

Add or extend functional tests so the first red bar comes from the public contracts Step `21.6` is meant to protect.

Recommended file split:

- one functional file for platform primitives such as connections and grants
- one functional file for capability-family and agent-scoped trading routes
- one focused event or WebSocket file if the existing route tests are too mocked to trust

Minimum API integration scenarios:

1. create a reusable connection for a user
2. derive or select the relevant trading binding
3. grant or bind that capability to an agent
4. observe readiness before and after the grant
5. hit agent-scoped trading state and action routes
6. revoke the grant and confirm readiness changes to `revoked` while audit history remains accessible

Favor lifecycles over isolated CRUD checks.

### 5. Add negative-path lifecycle coverage

Step `21.6` is incomplete if it only proves the happy path.

Minimum negative scenarios:

- binding exists but the agent is ineligible
- connection or binding is revoked after grant
- duplicate active grant is rejected or replaced according to the documented rule
- readiness returns `unconfigured` when the agent lacks the necessary binding
- action endpoints reject use when readiness is not effectively ready

These tests should target the shared readiness and revocation semantics defined in the architecture doc, not ad hoc family-specific guesses.

### 6. Strengthen shared event-envelope coverage on the real WebSocket surface

The redesign explicitly standardizes eventing. Cover that at the transport boundary clients consume.

Use the existing `/events` tests as the starting anchor.

Add scenarios that prove:

- the client receives a shared envelope, not a family-specific top-level shape
- the envelope fields remain stable: `id`, `timestamp`, `actorType`, `actorId`, `eventType`, `payload`
- capability events include `capabilityFamily` and `bindingId` when relevant
- user scoping is preserved so one user cannot receive another user's capability events

If the current event-route tests are too mocked to prove the envelope shape end to end, add a focused integration-style test that publishes a real envelope through the subscriber path.

### 7. Rewrite or retire legacy trading-first tests that now protect the wrong surface

Search for tests that still encode assumptions such as:

- `/bots` being the primary public execution surface
- venue-account-first setup being required for core agent flows
- mission-control summaries deriving truth from bot-shaped counts instead of agent state plus capability readiness

Apply this rule carefully:

- keep advanced-trading tests if the feature still exists as a secondary surface
- rewrite tests if the behavior remains but the primary API or UX entry point changed
- delete tests only when the product decision itself was explicitly rejected by the redesign

The suite should end this step smaller only where obsolete assumptions were removed, not because coverage was dropped.

### 8. Refactor Playwright helpers around agent-first capability setup

Update `tests/e2e/helpers.ts` so it no longer assumes a venue-first create flow.

The helper layer should support:

- registering and logging in a user
- creating an agent from the new agent-first flow
- opening the agent detail page
- creating or selecting platform resources needed for a capability
- binding or enabling a capability from the agent path

If API seeding is needed to keep journeys short, do it deliberately through the public API and document that choice in the test comments.

### 9. Add or rewrite Playwright journeys to match Step 21.6 acceptance stories

Use the existing journey files as anchors, but update them to validate the redesigned model.

Minimum journey set:

1. create agent from the primary flow and land on agent detail without bot-first setup
2. observe trading capability as `unconfigured` or equivalent when no binding is granted yet
3. add credential or connection as a reusable platform resource where the UI supports it
4. bind or grant the trading capability to the agent
5. observe readiness transition and the relevant primary CTA becoming usable
6. start or resume the capability from the agent surface
7. verify mission control reflects agent state correctly after the capability is active

If one full browser journey becomes too brittle, split it into two shorter journeys:

- setup and readiness
- execution and mission-control reflection

### 10. Run validation in increasing scope

Validate narrowly first, then widen.

Recommended order:

1. targeted functional test file for connections and grants
2. targeted functional test file for capability routes
3. targeted event or WebSocket test file
4. targeted Playwright journey files changed in this step
5. `scripts/shell/tests/run-all-tests.sh --e2e`
6. `pnpm lint`

Do not rely on `pnpm test` alone if Step `21.6` added or rewired functional and E2E coverage that has dedicated runners.

## Implementation Notes For The Agent

- Prefer replacing route-handler mocks with functional coverage when the behavior spans persistence, route wiring, or multiple resources.
- Keep narrow unit tests only where they still provide unique value, such as small branch logic in grant helpers.
- Make failures loud. If the app cannot yet support a capability-model journey, expose that gap with a failing test or a documented blocker rather than skipping silently.
- When a legacy bot-oriented route is still intentionally supported as an advanced surface, test it as advanced trading infrastructure, not as the platform's primary public truth.
