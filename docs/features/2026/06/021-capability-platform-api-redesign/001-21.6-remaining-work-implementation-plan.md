## Goal

Fully complete Step `21.6` by replacing the remaining trading-first test assumptions with executable coverage for the capability-platform model.

The finished suite must prove the public redesign through real app wiring and real user flows:

```text
platform resources -> capability grants/bindings -> readiness lifecycle -> shared events
                   -> agent-scoped capability actions -> mission-control reflection
```

This is not a test-count exercise. The objective is to make the test suite protect the new public truth:

- agents are the primary execution surface
- connections and credentials are reusable platform resources
- capability routes are the main operational API shape
- readiness and revocation follow the shared contract
- the shared event envelope is the only public event shape
- Playwright journeys follow agent-first capability enablement rather than bot-first trading setup

## Operating Rules For The Agent

Before implementing anything, hold these constraints constant:

1. Follow the implementation guide literally: update the parent plan before code, keep only one step in progress, and log deviations before implementing them.
2. Prefer functional API tests over mocked route tests whenever the behavior spans persistence, route registration, multiple resources, or lifecycle transitions.
3. Keep narrow handler or service tests only when they uniquely cover local branch logic cheaply.
4. Do not preserve legacy tests if they encode public assumptions the redesign explicitly rejected.
5. Do not hide missing product capability behind skipped tests. If the app cannot support a required path yet, expose the gap with a failing test or a documented blocker.
6. Validate in increasing scope after each slice: targeted Vitest first, targeted Playwright next where relevant, then broader suite runs, then `pnpm lint`.

## What Must Be True At The End

Treat Step `21.6` as complete only when all of the following are true:

- `apps/api/src/__tests__/functional/` proves the platform-resource and capability-route lifecycle against the real app builder
- duplicate grant, ineligible agent, readiness gating, and revocation semantics are covered beyond the happy path
- `/events` is covered through the shared `PlatformEventEnvelope` model rather than only mocked event assertions
- browser journeys prove the primary agent-first flow from agent creation to capability readiness and execution
- obsolete tests that protect trading-first or bot-first public assumptions have been rewritten or removed after replacement coverage exists
- the relevant targeted tests pass
- `scripts/shell/tests/run-all-tests.sh --e2e` passes in a suitable environment
- `pnpm lint` passes

## Step-by-Step Flow

### 1. Sync the plan state before touching tests

Open the parent plan and make it honest before editing code.

Actions:

1. Mark Step `21.6` as `in progress` in [000-plan.md](./000-plan.md) if it is not already.
2. Confirm the Decision Log already captures the UAT standardization on the existing Playwright journeys and `scripts/shell/tests/run-all-tests.sh`.
3. If implementation reality has changed since the remaining-work doc was written, append a Decision Log row before making any code or test changes.

Do not start by writing tests into a stale plan state.

### 2. Build a keep/rewrite/delete ledger for the current test surface

Before editing assertions, classify the current suite so the agent does not drift into random cleanup.

Required output of this audit:

- `keep`: still valid under the capability-platform model
- `rewrite`: still valuable behavior, but the route shape or public assumptions are outdated
- `delete`: protects a public model the redesign explicitly rejected

Start with the shortlist already identified in the remaining-work doc and expand outward only when a touched test clearly references:

- `/bots` as the main public execution surface
- venue-account-first setup as the required primary flow
- mission-control truth derived from bot summaries instead of agent state plus readiness

Rules:

- do not delete a test until replacement coverage exists
- do not rewrite a narrow local test if a functional test is the correct proof layer
- keep advanced-trading tests only when they still describe an intentionally retained advanced surface

### 3. Upgrade the functional harness first

Treat `apps/api/src/__tests__/functional/helpers.ts` as the gateway to the rest of Step `21.6`.

The harness must register every redesigned public surface required by the lifecycle tests, especially:

- `/events`
- `/credentials`
- existing connection, capability, agent, auth, and interactivity routes already used by the functional suite

Deliverable for this step:

- one realistic in-process app builder that can prove the capability lifecycle without a second parallel harness

Validation checkpoint:

- run targeted functional discovery or a small targeted functional test file immediately after the harness change

Suggested command:

```bash
pnpm exec vitest run --no-file-parallelism apps/api/src/__tests__/functional/capability-model.functional.test.ts
```

### 4. Extend capability-model functional coverage before touching broader test cleanup

Use `apps/api/src/__tests__/functional/capability-model.functional.test.ts` as the main anchor.

Add or extend coverage for the redesign claims that still lack proof on the real app surface:

1. duplicate active grant protection or replacement behavior
2. ineligible-agent readiness cases
3. action rejection when readiness is not effectively ready
4. readiness transitions after connection or binding revocation
5. audit visibility surviving revoke and regrant flows

Target posture:

- one coherent lifecycle-oriented file is better than several tiny CRUD files
- use real route calls and persistence effects rather than service mocks
- prove both family-level and agent-scoped route behavior when the lifecycle depends on both

Validation checkpoint:

```bash
pnpm exec vitest run --no-file-parallelism apps/api/src/__tests__/functional/capability-model.functional.test.ts
```

### 5. Add focused functional coverage where capability-model tests would become too overloaded

If `capability-model.functional.test.ts` starts to mix unrelated concerns, split only where the split mirrors a real contract boundary.

Good reasons to add another functional file:

- event transport requires a distinct setup pattern
- export coverage needs separate rewrite work
- a second capability-lifecycle file improves readability without duplicating fixtures

Bad reasons to split:

- avoiding a slightly longer test file
- preserving old mocked test boundaries
- isolating behavior that is only meaningful as a multi-resource lifecycle

Prefer naming by public contract, for example:

- `capability-events.functional.test.ts`
- `capability-exports.functional.test.ts`

### 6. Prove the shared event envelope on the real `/events` surface

The redesign settles one shared event model. Step `21.6` is not complete until transport-level tests prove it.

Use `apps/api/src/routes/events.test.ts` as the nearest anchor, but move the source of truth to a test that demonstrates real envelope behavior.

Required assertions:

1. the client receives a `PlatformEventEnvelope`, not a family-specific top-level shape
2. stable envelope fields are present: `id`, `timestamp`, `actorType`, `actorId`, `eventType`, `payload`
3. `capabilityFamily` and `bindingId` are present when the event is capability-scoped
4. user scoping prevents one user from receiving another user's events

Implementation guidance:

- if the existing route test can prove this with real app wiring, extend it
- if it remains too mocked, add a focused functional or integration-style event test and keep the route test narrow

Validation checkpoint:

```bash
pnpm exec vitest run apps/api/src/routes/events.test.ts
```

If the route test is no longer the main proof, also run the new functional event file directly.

### 7. Narrow or retire mocked route and service tests after the functional replacements are green

Only after the real lifecycle coverage exists should the agent prune the old tests.

File-by-file rule:

- `apps/api/src/routes/connections.test.ts`: keep only cheap local branching that functional tests do not cover better
- `apps/api/src/routes/capabilities/trading.test.ts`: keep state-machine or request-shape checks that are still uniquely local
- `apps/api/src/routes/events.test.ts`: keep transport-edge assertions only if they add value beyond the new real-surface test
- `apps/api/src/routes/credentials.test.ts`: keep only if credentials still have meaningful narrow branch behavior outside the broader lifecycle tests
- `apps/api/src/grant-service.test.ts`: keep only append-only or transition-specific branch coverage that would be awkward to prove repeatedly at the HTTP layer

Delete tests only when they protect a rejected public contract.

Validation checkpoint:

```bash
pnpm exec vitest run \
  apps/api/src/routes/connections.test.ts \
  apps/api/src/routes/capabilities/trading.test.ts \
  apps/api/src/routes/events.test.ts \
  apps/api/src/routes/credentials.test.ts \
  apps/api/src/grant-service.test.ts
```

### 8. Audit functional export coverage for bot-first assumptions

The remaining-work doc specifically calls out `apps/api/src/__tests__/functional/exports.functional.test.ts`.

Audit it for assertions that still assume:

- bots are the primary public execution unit
- export eligibility is expressed through legacy trading-first nouns
- the API contract should expose the old public product frame

Decision rule:

- rewrite if the export behavior still exists under the new public model
- delete only if the test protects a surface the redesign explicitly removed

Do not remove export coverage without an intentional replacement or an explicit product decision.

Validation checkpoint:

```bash
pnpm exec vitest run --no-file-parallelism apps/api/src/__tests__/functional/exports.functional.test.ts
```

### 9. Keep the Playwright helper layer honest about the current product surface

Use `tests/e2e/helpers.ts` to support the agent-first flows without inventing hidden capabilities the public app does not expose.

Rules for helpers:

- prefer public-API or public-UI setup whenever practical
- keep `seedTradingBinding(...)` explicitly test-internal
- use direct DB seeding only where the product still lacks a public binding-creation surface
- document the seeding reason in the relevant test when it remains necessary

The helper layer should cleanly support:

- user registration and login
- agent creation
- agent detail navigation
- connection creation
- trading capability bind or grant flow
- binding seeding where the UI still lacks a public equivalent

Validation checkpoint:

```bash
pnpm --dir tests/e2e test -- --list
```

### 10. Strengthen the critical Playwright journeys in capability-first order

Use the existing journeys already identified as the critical path.

Required sequence:

1. keep `tests/e2e/journeys/07-mission-control-renders.spec.ts` as the shell and empty-state truth
2. keep and strengthen `tests/e2e/journeys/08-mission-control-capability-reflects.spec.ts` as the core readiness journey
3. audit `tests/e2e/journeys/04-safety-alert-visible.spec.ts` for stale trading-first assumptions
4. update `tests/e2e/journeys/01-signup-create-agent.spec.ts` only where the create flow or post-create landing assertions still encode outdated product framing

Minimum browser acceptance story that must be executable by the end:

1. register and create an agent from the primary flow
2. land on agent detail without being forced through bot-first setup
3. observe capability readiness in an `unconfigured` or equivalent pre-bind state
4. create or select a reusable connection
5. bind or grant the trading capability to the agent
6. observe readiness transition to a usable state
7. trigger the primary capability action from the agent surface
8. verify mission control reflects the resulting agent truth honestly

If one spec becomes too long or brittle, split by story boundary:

- setup and readiness
- execution and mission-control reflection

### 11. Run validation in increasing scope after each edit slice

Do not jump straight to the broadest command after every small change.

Recommended validation ladder for this step:

1. targeted Vitest file you just touched
2. targeted neighboring functional file if the change affects shared fixtures
3. targeted Playwright listing or specific journey file when browser helpers changed
4. `pnpm test:functional`
5. `scripts/shell/tests/run-all-tests.sh --e2e`
6. `pnpm lint`

Suggested concrete commands:

```bash
pnpm exec vitest run --no-file-parallelism apps/api/src/__tests__/functional/capability-model.functional.test.ts
pnpm exec vitest run apps/api/src/routes/events.test.ts
pnpm test:functional
pnpm --dir tests/e2e test -- --grep "mission control|capability"
scripts/shell/tests/run-all-tests.sh --e2e
pnpm lint
```

Use the narrowest command that can falsify the current slice first.

When the suite is green and the obsolete assumptions are removed, close the documentation loop.

Actions:

Do not leave the code green while the plan still claims the work is pending.
