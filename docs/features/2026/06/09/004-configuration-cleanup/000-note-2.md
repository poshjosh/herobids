# docker compose files

**What Compose Is For**

docker-compose.yaml and docker-compose.dev.yaml are infrastructure wiring, not the canonical home of operator policy.

In this repo, they should do three things:

- wire services together
- inject deployment-specific env into long-running processes like `api` and `worker`
- pass secrets or infra values into the `worker` when the `worker` is responsible for forwarding a narrow subset into spawned agent containers

That means compose is the right place for values like:

- service connection URLs such as `DATABASE_URL` and `REDIS_URL` in docker-compose.yaml
- local-dev defaults like `AUTH_FRONTEND_ORIGIN` and `WEB_PORT` in docker-compose.yaml and docker-compose.dev.yaml
- docker runtime wiring like `DOCKER_HOST`, `DOCKER_NETWORK`, `AGENT_IMAGE`, and `AGENT_RUNTIME_MODE` in docker-compose.yaml
- LLM API secrets that must reach the worker so the worker can explicitly forward them into spawned agent containers, as seen in docker-compose.yaml and docker-agent-manager.ts

**What Compose Is Not For**

Compose should not become a second full operator-config surface for structured policy.

So it should not carry things like:

- `TRADING_HOURS_JSON`
- `MARKET_DATA_CONFIG_JSON`
- nested market-data budgets and TTLs
- other structured policy that already lives cleanly in default.yaml and schema.ts

Those values should remain in typed operator config, then the worker should derive and forward only what the agent runtime needs. That is already what happens in index.ts and docker-agent-manager.ts:

- `appConfig.llm.tradingHours` becomes `llmTradingHoursJson`, then `TRADING_HOURS_JSON`
- `appConfig.marketData` becomes `marketDataConfigJson`, then `MARKET_DATA_CONFIG_JSON`

That is the right separation. Compose should not know or care about those internal payload names.

**How To Think About The Current Compose Files**

docker-compose.yaml
- Good fit:
  `DATABASE_URL`
  `REDIS_URL`
  `DOCKER_HOST`
  `DOCKER_NETWORK`
  `AGENT_IMAGE`
  `AGENT_RUNTIME_MODE`
  `LLM_API_KEY*`
- Reason:
  these are service wiring, infrastructure selection, or secrets/pass-through values needed by the worker process

docker-compose.dev.yaml
- Good fit:
  `NODE_ENV`
  `LOG_FORMAT`
  `AUTH_FRONTEND_ORIGIN`
  `VITE_API_PROXY_TARGET`
  `WEB_PORT`
- Reason:
  these are dev-runtime concerns, not long-lived operator policy

**The Important Subtlety**

Compose is especially important here because Docker Compose does not magically pass host .env values into containers unless the service explicitly declares them. The config guide already calls that out in configuration.md.

That means if the agent container needs an LLM API key, the flow is:

1. host environment or secret source
2. compose passes `LLM_API_KEY*` into the `worker`
3. the `worker` explicitly forwards only the needed keys into the spawned agent container in docker-agent-manager.ts

That is a valid use of compose. It is not the same thing as making compose the home of business policy.

**My Recommendation**

Treat the compose files as the place for:

- infrastructure wiring
- local-dev defaults
- secret passthrough into `worker`
- explicit env that the `worker` must receive before it can launch agent containers

Do not use the compose files for:

- structured operator policy already modeled in typed config
- internal worker-to-agent derived payload values
- duplicating large parts of default.yaml

**Concrete Guidance For An Implementing Agent**

Keep in compose:
- `DATABASE_URL`
- `REDIS_URL`
- `DOCKER_HOST`
- `DOCKER_NETWORK`
- `AGENT_IMAGE`
- `AGENT_RUNTIME_MODE`
- `LLM_API_KEY`
- `LLM_API_KEY_OPENROUTER`
- `LLM_API_KEY_ANTHROPIC`
- `LLM_API_KEY_OPENAI`
- other true secrets or infra-specific values that must reach `worker`

Probably acceptable in compose, but optional:
- `LLM_PROVIDER`
- `LLM_MODEL`
- `LLM_BASE_URL`

Why:
- they already map to operator config overrides in config.ts
- but they are not secrets, so if you want stricter discipline you could remove them from compose and let YAML be authoritative

Do not add to compose:
- `TRADING_HOURS_JSON`
- `MARKET_DATA_CONFIG_JSON`
- nested `MARKET_DATA_*` policy unless there is a very specific deployment reason
- other structured policy already represented in schema.ts

Why:
- those should be resolved from typed operator config, not injected as a parallel compose-only policy layer

**Checklist**

1. Keep docker-compose.yaml focused on service wiring, secrets passthrough, and docker runtime selection.
2. Do not add trading-hours or full market-data policy env vars to the compose files.
3. Keep default.yaml as the canonical place for trading hours and market-data operator policy.
4. Keep index.ts responsible for deriving container payload fields from resolved config.
5. Keep docker-agent-manager.ts responsible for explicit secret forwarding into agent containers.
6. Decide whether `LLM_PROVIDER`, `LLM_MODEL`, and `LLM_BASE_URL` should remain in compose as optional override passthroughs or be removed for stricter YAML-first discipline.
7. Document in configuration.md that compose is infra wiring, not a second home for structured operator policy.

**My Default Call**

If I were implementing this today, I would keep the compose files mostly as they are for:
- `DOCKER_HOST`
- `DOCKER_NETWORK`
- `AGENT_IMAGE`
- `AGENT_RUNTIME_MODE`
- `LLM_API_KEY*`

I would not add any compose entries for trading hours or market-data policy.

For `LLM_PROVIDER`, `LLM_MODEL`, and `LLM_BASE_URL`, I think either approach is defensible:
- keep them as optional compose passthroughs for deployment convenience
- or remove them and force YAML to be the only source for non-secret LLM runtime settings

If you want the stricter version of the rule, I would remove those three from docker-compose.yaml and leave only secrets plus infra wiring there.
