A good test is: agent mid-tick receives SIGTERM, stops opening new work, exits cleanly within timeout, and the new worker does not duplicate action.
5. Add Telegram idempotency and cold-start anchor tests for plans 011 and 012. Route coverage is already broad in agent-interactivity.test.ts, including reply routing, slash routing, broadcast, and default routing. 6. Add a Playwright provider-catalog journey for plan 008. The backend contract is already covered in providers.test.ts, but there is still high value in one browser flow that proves credentials and connections render from the fetched catalog, filter compatible credentials, and handle custom mode cleanly.
7. Add a Playwright billing journey for plan 010. The config and API surfaces are already covered in billing-config.test.ts and billing.test.ts, but the plan’s real promise is UI behavior: billing page always visible, usage sections render empty states, and provider choice is decoupled from dashboard visibility.
8. Add a browser-plus-runtime risk-config test for plan 009. API bounds and persistence are already in agents.test.ts, but the missing test is the two-path behavior the plan cares about: explicit user-set limits remain hard caps, blank fields fall back to platform defaults and stay agent-adjustable.

**Gaps And Deferred Work**

1. 001-plan.md is duplicated in-place after the first exit criteria. That is a planning hygiene gap on its own if this backlog is meant to be canonical.
2. Plan 001 still leaves open decisions around invalid fork behavior, stable error-code shape, and whether to expose the tool manifest later for a skill editor in 001-plan.md.
3. Plan 002 intentionally does not auto-delete removed system skills. Manual migration is still required for removals in 001-plan.md.
4. Plan 003 still leaves open semantic questions: whether wall-clock expiry should remain stopped, whether graceful runtime activity should use a stopped event type rather than started, and whether runtime sessions should later store explicit terminal reasons in 001-plan.md.
5. Plan 004 is explicitly phased. The current recommendation is only application-level graceful shutdown; rolling replacement and fencing-token safety are later phases in 000-graceful-agent-deployment.md. It also deliberately excludes hot state migration and multi-worker failover in 000-graceful-agent-deployment.md.
6. Plan 005 intentionally does not remove bots.venueAccountId or migrate downstream fills, positions, orders, or reconciliation away from venue-account anchoring in 005-trading-binding-native-bot-startup-follow-through.md. So even after the startup migration, legacy identifiers remain part of the runtime model.
7. Plan 006 deliberately leaves maxToolCallsPerTurn and maxToolCallsPerTick for later in 001-plan.md. The main remaining risk there is configuration consumption drift rather than schema coverage; the integration guard at config-propagation.integration.test.ts helps, but this is still a place where “parsed” and “actually used” can diverge.
8. Plan 007 is still an ideal-state document, not a concrete delivery plan. The biggest unresolved gaps are the actual capability or subscription eligibility model, rollout compatibility while old producers or consumers exist, and the final removal of legacy generic wake semantics in 001-ideal-state-plan.md and 001-ideal-state-plan.md.
9. Plan 008 still includes a real migration and audit step for existing free-text provider values in REVISED.md. The product gap is no longer route validation; it is migration safety and browser behavior.
10. Plan 009 explicitly defers the runtime adjust-risk tool and real-time notifications in 001-plan.md. The adjacent review notes also suggest one unresolved product question: whether percentage-based limits without a capital baseline are meaningful enough to allow.
11. Plan 010 intentionally does not redesign the billing model, rate cards, or live-trading rules in 001-plan.md. The real ongoing gap there is guarding against a new shadow “enabled” flag sneaking back in under a different name.
12. Plan 011 explicitly leaves slash commands, inline keyboards, per-agent bot tokens, and multi-user shared bots out of scope in 001-plan.md. It also depends on a public HTTPS webhook URL in dev, which is an operational caveat rather than a code gap.
13. Plan 012 defers reply threading, /agents listing, and all other slash commands in 001-plan.md. The adjacent review notes also flag a parser-design risk: target parsing should stay pure and not depend on known-agent-name lookup.
14. Plan 013 has the largest explicit blockers. It depends on plan 022 and plan 023 in 013-backtesting-agent-tools.md, rejects LLM strategy backtests, does not support true mid-run cancellation, caps date ranges, and leaves open questions about the 90-day window and limited momentum parameters in 013-backtesting-agent-tools.md. Also, because backtests.test.ts already exists, this backlog item probably needs a re-baseline before more work.
15. Plan 014 is intentionally narrow: Solana-only, opt-in, no CoinMarketCap discovery or enrichment, and no execution or strategy changes in 001-plan.md. Like backtesting, it already has partial repo foundations, so the remaining gap is completion, not greenfield design.
16. Plan 015 has the heaviest explicit deferral list: no orderbook depth, fills or orders, per-user exposure, charting, UI symbol selection, acknowledgements, or auto-remediation in 001-plan.md. Its biggest open question is whether stream health is required for v1 or deferred, plus symbol naming and warning-threshold ownership in 001-plan.md.
