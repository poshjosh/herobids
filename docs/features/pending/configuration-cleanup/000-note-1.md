**Recommended Policy**

In this repo, configuration.md already gives the right rule set:

- operator config lives in YAML and is validated at startup
- environment variables are part of the resolution chain, but should be used sparingly
- secrets should not live as ordinary config values
- agent containers must receive only the narrow runtime payload they need
- process.env should not be read outside the config loader, except for clearly documented infrastructure exceptions

That means schema.ts and default.yaml are the right home for structured policy like trading hours, rate limits, discovery budgets, cache TTLs, and other operator-tuned behavior.

The worker already converts resolved operator config into the agent-container payload in index.ts. You can see that with the existing forwarding of llmTradingHoursJson and marketDataConfigJson there. So there is no need to create a second operator-facing env surface just because the container eventually consumes the value.

**Why This Is The Right Boundary**

The important distinction is not YAML versus env. The important distinction is who owns the value and what lifecycle it has.

Values that should stay in operator config:
- structured policy
- non-secret deploy-time defaults
- nested provider budgets and thresholds
- things operators should understand by reading default.yaml

Values that can justify env overrides:
- secrets or secret-backed values
- a small number of simple deployment-specific scalars that infra genuinely injects
- infrastructure wiring that may differ per deployment target

Values that are not operator config at all:
- internal payload passed from worker to isolated agent runtime
- transient contract fields like llmTradingHoursJson and marketDataConfigJson in index.ts

If you add env overrides for every nested config field, you create two operator interfaces for the same policy. That increases drift, makes default.yaml less authoritative, and pushes the codebase away from its own documented rule that the default config file is the primary documentation.

**What To Implement**

The implementation should explicitly separate three categories.

Category 1: Keep YAML-only
- llm.tradingHours in schema.ts and default.yaml
- most of marketData in schema.ts, especially nested budgets, cache TTLs, and provider tuning
- any other structured operator policy that is not a secret and does not need infrastructure-time injection

Category 2: Allow env override
- secret or secret-like fields such as Birdeye and CoinMarketCap API keys
- possibly provider enabled flags if operators genuinely toggle them via deployment env
- possibly base URLs when they are deployment-specific rather than product policy
- existing scalar LLM runtime values already following the project pattern in config.ts, such as provider, model, timeout, and intervals

Category 3: Internal container payload only
- llmTradingHoursJson in index.ts
- marketDataConfigJson in index.ts
- AGENT_CONFIG and other worker-to-agent runtime contract values mentioned in runtime-boundary-and-message-contract.md

Those should continue to be derived from resolved config, not introduced as new operator env variables.

**Detailed Guidance For The Implementing Agent**

config.ts
- Remove the idea of adding LLM_TRADING_HOURS_JSON as an operator env override.
- Do not add a broad set of market-data env overrides just because the schema now contains those fields.
- Keep ENV_OVERRIDES focused on:
  DATABASE_URL, REDIS_URL, and similar top-level deployment values
  existing LLM scalar overrides that already fit the current pattern
  provider API keys or other genuine secret-backed fields if the project wants them overrideable
- If you add any new env overrides here, the burden of proof is operational need, not schema existence.
- Document that empty-string passthrough values must continue to be ignored so deployment stubs do not stomp YAML defaults.

schema.ts
- Keep tradingHours as typed operator config. It is correctly placed already.
- Add fail-fast validation for paid providers:
  if birdeye.enabled is true, birdeye.apiKey must be non-empty
  if coinMarketCap.enabled is true, coinMarketCap.apiKey must be non-empty
- Consider whether a future secrets-manager reference field is better than a raw apiKey field, but do not widen scope unless the repo already has that pattern.
- Do not move llmTradingHoursJson or marketDataConfigJson into the schema. Those are transport payloads, not operator-config fields.

default.yaml
- Keep trading hours documented here as the operator-facing control surface.
- Add comments clarifying that this is the canonical place for structured policy like market-data budgets and tick gating windows.
- If you add comments for paid providers, make the enabled plus missing-key rule obvious.
- If you decide some values are intentionally YAML-only, say so in comments or in the config best-practices doc so future contributors do not reopen the same question.

index.ts
- Keep forwarding resolved config into container payloads:
  llmTradingHoursJson from appConfig.llm.tradingHours
  marketDataConfigJson from appConfig.marketData
- Do not add a parallel path where the container gets these values directly from operator env.
- Review the remaining raw process.env reads for DOCKER_HOST, DOCKER_NETWORK, and AGENT_IMAGE.
- Decide one of two things:
  either keep them as documented infrastructure exceptions
  or promote them into typed operator config and source them from appConfig
- My recommendation is to treat those three as infrastructure exceptions unless you expect operators to manage them as product config in YAML.

configuration.md
- Add one short clarifying section that says:
  schema presence does not automatically imply env override support
  structured operator policy belongs in YAML first
  env overrides are for narrow operational cases, especially secrets and deployment wiring
  worker-to-agent JSON payload fields are internal contract, not operator env surface
- This is the most important documentation change because it prevents future drift.

config.test.ts
- Do not add tests for a new trading-hours env override, because the recommendation is not to add one.
- Keep the existing YAML-based trading-hours coverage.
- If you add env overrides for provider API keys or enabled flags, add narrow tests only for those.
- Add negative tests for fail-fast provider validation once schema refinements are added.

**Suggested Default Decisions**

If the implementing agent needs defaults rather than reopening design questions, these are the decisions I would want it to take:

- Decision: no env override for trading hours
- Decision: no env override for nested market-data budgets by default
- Decision: env override allowed for Birdeye and CoinMarketCap API keys only if the repo still relies on deployment env passthrough for local or infra use
- Decision: llmTradingHoursJson and marketDataConfigJson remain worker-derived container payloads only
- Decision: DOCKER_HOST, DOCKER_NETWORK, and AGENT_IMAGE remain documented infrastructure exceptions unless there is a clear need to expose them in YAML

**Acceptance Criteria**

The implementing agent should consider this done when all of the following are true:

- default.yaml remains the canonical documented source for llm.tradingHours and marketData policy
- config.ts does not introduce LLM_TRADING_HOURS_JSON
- index.ts still derives container payload fields from resolved appConfig
- schema.ts fails fast when a paid provider is enabled without its required key
- configuration.md explicitly documents the boundary between operator YAML, narrow env overrides, and internal container payload
- config.test.ts covers any new allowed env overrides and the provider validation behavior
- there is no new parallel operator interface for structured policy that already lives cleanly in YAML

**One Subtle Point Worth Calling Out**

The repo rule is not literally “only secrets in env vars.” The real rule is closer to this:

- secrets should not live as normal checked-in config
- env overrides are allowed in the operator-config chain
- but they should be narrow, intentional, and mostly about deployment concerns
- structured operator policy should still prefer YAML
- internal worker-to-agent payload is neither YAML nor operator env; it is a transport contract

That is why your pushback on trading-hours env override is correct. The existence of a container payload does not justify creating an operator env variable for the same value.
