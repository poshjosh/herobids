# Bug Report: documents uploaded during agent creation/edit are never seen by the agent

- **Status:** FIXED (in code, not deployed)
- **Severity:** Medium
- **Date:** 2026-11-15
- **Discovered By:** Manual report. Agent `job-searcher` (id `147f97ee-41c6-414b-b297-5b1dda3f1d21`) was created with a CV attached via the create-agent form (object/prompt field's file picker). The agent never acted on the CV. The same CV, sent later via web chat, was seen and used by the agent. Reproduced consistently.
- **Summary:** `POST /agents/:id/documents` — the route behind the create-agent and edit-agent file pickers — stores the file and extracts its text correctly, but never tells the agent it exists. The agent only ever learns a document's id through a notice message that reaches its own Redis inbound stream (`agent:outbound:{agentId}`); today that notice is produced only by the web-chat message handler and the Telegram document webhook, not by the control-plane upload route.

## Symptom

- A document uploaded during agent creation (file picker in the create-agent form) or agent edit (edit modal) lands in `agent_documents` with `extractionStatus: 'ready'`, but the agent never mentions it, never calls `read_agent_document`, and gives no sign it knows the document exists.
- The same file, if resent as a chat attachment on `POST /agents/:id/message`, works immediately: the agent reads it via `read_agent_document`.
- No error is logged anywhere in this flow. The upload returns 201 with correct document metadata.

## Investigation

- The only place an agent currently discovers a document's id is `buildDocumentNoticeText` (`packages/documents/src/agent-document-notice.ts`), a short text block naming the `documentId` and pointing at the `read_agent_document` tool.
- Across the whole `apps/` tree, `buildDocumentNoticeText` is called from exactly two places, both in `apps/api/src/routes/agent-interactivity.ts`:
  - the web-chat message handler (`POST /agents/:id/message`, ~line 589), which records the notice in the agent's conversation then publishes it to `agent:outbound:{agentId}` under the recorded row's id;
  - the Telegram document webhook (~line 1320), which delivers the notice via `ChatInboundRouter.deliver` (`chat-inbound-router.ts`) — a bare publish, no row recorded for this one.
- `apps/api/src/routes/agent-documents.ts`, `POST /agents/:id/documents` (lines 42–93) — the route behind both the create-agent file picker (`CreateAgentFlow.tsx` ~lines 540–548, called before the agent is started) and the edit-agent file picker (`EditAgentModal.tsx` ~lines 470–474) — stores the document via `AgentDocumentService.uploadDocument()` and returns its metadata as the HTTP response. It never produced any notice and had no Redis client at all (the route module's original signature was `(app, db)`).
- Checked whether a notice published to the Redis stream before the agent's first start would be lost: it would not be, in the common case. `OutboundInbox.ensureGroup` (`apps/worker/src/agents/outbound-inbox.ts:144`) creates the consumer group at stream position `'0'` with `MKSTREAM`, so the agent's first read sees everything already on the stream, including a notice published before the agent ever started. The stream is only deleted by `cleanupEphemeralAgentRedisState`, called on session stop, session end, crash, and startup-timeout expiry (`apps/worker/src/agents/agent-session-manager.ts:634, 684, 748, 1047`) — none of which run between agent creation and first start in the normal case.
- Also checked, and ruled out, an alternative fix built on `announceSessionStarted` (`apps/worker/src/session-started-message.ts`), which records a `senderType: 'platform'` row via `conversations.service.recordPlatformMessage`. That row is visible to the human in the web/Telegram thread, but the agent's own conversation-history rebuild explicitly discards it: `windowEntryFromConversationRow` (`apps/worker/src/conversation-window.ts:107`) returns `null` for `senderType === 'platform'` rows. A fix built on that mechanism would not reach the agent and was not pursued.
- **Checked during code review (see Change Log) whether a bare stream publish with no conversation row would actually reach the agent, and whether it would survive a restart:**
  - It does reach a running agent's current tick: `extractUserMessageText` (`apps/worker/src/tick-gate-state.ts`) reads the text straight off the envelope's `payload.message`, and the live tick-processing loop (`apps/worker/src/agent.ts` ~line 2996) builds a conversation-window entry from that text for any `user.message`/`agent.user.message` envelope sitting on the stream — no database lookup by `messageId` is involved in this path. `messageId` itself is used only for a client-side in-memory dedup check (`metrics.conversationWindow.some(...)`) and for an activity-log field, neither of which requires the id to correspond to a stored row.
  - It does **not** survive a restart. `hydrateConversationWindow` (`apps/worker/src/agent.ts` ~line 1481), which rebuilds the conversation window from scratch on every process start (including the agent's very first tick after creation), reads only from `conversationService.listThread(...)` — the DB-backed `conversation_messages` table. A notice that was only ever published to Redis, with no row ever written, is invisible to this rehydration. Net effect: a bare-publish notice reaches the agent's first tick (since that tick also live-captures the fresh stream envelope in the same pass), but is gone from the record if the agent restarts afterward — the opposite of durable.
  - This ruled out shipping the fix as a bare `redisClient.xadd(...)` with no conversation row (the form this fix originally shipped in), in favor of recording the notice the same way the chat path's own primary call site does: `conversations.service.recordUserMessage(...)` first, then publish under the returned row id, then `markDelivery`. See Fix, below.

## Root Cause

`agentDocumentRoutes` (`apps/api/src/routes/agent-documents.ts`) had no path from a successful upload to the agent's inbound Redis stream, and no way to record that a notice had ever been sent. The web-chat path records a notice as a real conversation row and publishes it under that row's id; the control-plane upload route did neither.

## Fix (direct notice on upload; no sweep, no backfill, no agent-running check)

- `apps/api/src/routes/agent-documents.ts`:
  - `agentDocumentRoutes` now takes a `redisClient: Redis` parameter and a `conversationRouteDeps` parameter (optional, defaulting to `createConversationRouteDeps(db)` for tests only — the real caller must pass the app's one shared instance; see the `index.ts` bullet below).
  - On a successful `POST /agents/:id/documents`, `notifyAgentOfDocument`:
    1. records a short, human-readable row in the agent's conversation — `body: "Uploaded ${filename}"`, `channel: 'web'` — via `conversations.service.recordUserMessage(...)`. This is what the web chat thread shows the creator; it reads as a normal chat message, not a tool instruction.
    2. builds the full notice text with `buildDocumentNoticeText({ documentId, filename, caption })` (naming the document id and the `read_agent_document` tool) and publishes *that* text — not the row's caption body — to `agent:outbound:{agentId}` via `ChatInboundRouter.deliver(...)`, under the recorded row's id and `queuedAt`.
    3. marks the row `sent` on a successful publish, or `failed` (one attempt, not retried) if the publish throws.
  - This mirrors the web-chat attachment path (`agent-interactivity.ts`) exactly: there too, the stored conversation row is the user's own typed caption (or nothing), while the full notice text exists only in the published Redis envelope and is never written back to any row. Reusing `ChatInboundRouter.deliver` (already the Telegram path's own publish call) for the publish step avoids a third hand-rolled envelope/`xadd` construction (the web-chat handler, Telegram, and this route would otherwise each build one).
  - The whole sequence is best-effort end to end: a failed record, or a failed publish, is logged and swallowed rather than failing the upload's HTTP response. The document is already safely stored and extracted by this point regardless of whether the notice succeeds.
- `apps/api/src/index.ts`: passes the app's one shared `conversationDeps` (constructed once near the top of the file with `appConfig.messaging.conversations`, and already given to `agentInteractivityRoutes` and `peerThreadRoutes`) into `agentDocumentRoutes(app, db, redisClient, conversationDeps)`, alongside the already-constructed `redisClient`. Passing this explicitly — not relying on the parameter's default — matters: the default builds a second `ConversationService` with schema-default limits instead of the operator-configured ones, which a first pass at this fix shipped with by mistake (caught in code review; see Change Log).

Explicitly out of scope (a decision brief recommends a durable, standing-fact design — list documents via a worker-side tool and a system-prompt section rebuilt every tick — as the long-term fix; this change is the smaller, direct fix only):

- No "is the agent currently running" check — the notice is recorded and published unconditionally, relying on the Redis stream surviving from creation to first start (verified above).
- No backfill of documents uploaded before this fix shipped.
- No change to `GET /agents/:id/documents` or to the agent-facing document-listing/tool surface.
- Known residual gap, accepted for this fix, restated precisely after a prior draft of this report overstated it: a startup timeout between upload and the agent's first successful boot wipes the Redis stream, so the *live* publish (the one carrying the full `read_agent_document` notice) is lost for that boot. The conversation row itself survives (it is marked `sent`, since the publish call did not throw — the stream accepted the write; the timeout happens afterward), and `windowEntryFromConversationRow` keeps `sent` user rows, so the next successful boot's `hydrateConversationWindow` does put the row back into the agent's conversation history. But the row's body is the short caption ("Uploaded cv.pdf"), not the full notice — the notice text was never written to any row, only published live. So the agent, on its next successful boot, sees a caption-only row in its history rather than a fresh instruction naming a document id, and whether it reasons from that alone to call `read_agent_document` again is unverified. The gap is narrower than "the agent never finds out" — it is "the agent's history shows that something was uploaded, but not, after a lost publish, which document id to read."
